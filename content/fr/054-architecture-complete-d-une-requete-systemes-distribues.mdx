# Architecture Complète d'une Requête : Du Navigateur au Cloud et BDD

Un vendredi à 18h30, les alertes Datadog hurlent : la latence P99 de votre endpoint de commande e-commerce vient d'exploser, passant de **85 ms à 4,2 secondes**. 

Les développeurs juniors accusent immédiatement la base de données. L'administrateur système incrimine le réseau cloud. Pourtant, les métriques CPU de la base PostgreSQL sont calmes à 12 %. 

Où est passée la requête ? Est-elle bloquée dans le TLS Handshake ? Dans la file d'attente du reverse proxy ? Dans un verrou d'un middleware d'authentification ? Ou dans l'épuisement du pool de connexions SQL ?

Pour concevoir des architectures robustes et déboguer avec une précision chirurgicale, un développeur senior ne peut pas voir une requête comme un simple appel `fetch('/api/order')`. Il doit maîtriser **l'intégralité du pipeline d'ingénierie distribué**.

## La Topologie Complète de la Requête Moderne

Voici la chaîne de traitement complète traversée par une requête dans une infrastructure cloud moderne :

```txt
[ CLIENT / BROWSER ]
       │
       ▼ (1. Résolution DNS Anycast & Tunnel TLS 1.3 / HTTP/3 QUIC)
[ EDGE CDN / CLOUD NETWORK (Cloudflare, AWS CloudFront) ]
       │ (WAF, Atténuation DDoS, Cache statique, Edge Workers)
       ▼ (2. Routage L4/L7 & Terminaison TLS)
[ INGRESS / LOAD BALANCER & API GATEWAY (Envoy, Nginx, Kong) ]
       │ (Rate Limiting distribué, Auth JWT, Circuit Breaker, Service Discovery)
       ▼ (3. Réseau Privé VPC / Service Mesh mTLS)
[ SERVICE APPLICATIF (Node.js, Go, Spring Boot) ]
       │ ├── Middleware (Tracing W3C traceparent, Validation Zod)
       │ ├── Clean Architecture (Controller -> UseCase -> Domain)
       │ └── Cache-Aside (Redis Cluster)
       ▼ (4. Connection Pooling - PgBouncer)
[ BASE DE DONNÉES TRANSACTIONNELLE (PostgreSQL Primaire & Réplicas) ]
       │
       ▼ (5. Asynchrone / Transactional Outbox)
[ MESSAGE BROKER (Apache Kafka / RabbitMQ) ]
```

## 1. L'Edge Layer : Le Premier Rempart Réseau

Avant même que votre serveur d'application ne soupçonne l'existence de la requête, celle-ci frappe le réseau périphérique (**Edge**).

### A. Anycast DNS & Routage Géographique
Le client résout le nom de domaine via le protocole Anycast. Plusieurs centaines de points de présence (PoP) à travers le monde partagent la même adresse IP publique. Le protocole BGP (Border Gateway Protocol) route automatiquement les paquets vers le routeur le plus proche du client en nombre de sauts réseau.

### B. WAF (Web Application Firewall) & Filtrage DDoS
À l'Edge, des moteurs de sécurité inspectent les paquets :
- Vérification des signatures d'attaques courantes (injections SQL, XSS, Path Traversal).
- Analyse comportementale contre les attaques par déni de service distribué (SYN Flood, HTTP Flood).
- Si la requête est malveillante, elle est rejetée par une erreur `403 Forbidden` à la périphérie, sans consommer la moindre ressource sur vos serveurs internes.

## 2. Ingress & API Gateway : L'Orchestration d'Entrée

Une fois le périmètre réseau franchi, la requête pénètre dans votre infrastructure cloud (VPC) via l'**API Gateway**.

```txt
Requête HTTP Entrante
        │
        ├──> [ Rate Limiting Token Bucket ] (Redis Centralisé)
        ├──> [ Validation du JWT ] (Clé publique JWKS asynchrone)
        ├──> [ Injection Tracing ] (w3c traceparent & baggage)
        └──> [ Circuit Breaker ] ──> Route vers Instance Saine
```

### Rôles de l'API Gateway moderne :
1. **Terminaison TLS & Déchargement SSL :** L'Edge ou l'Ingress décrypte le trafic HTTPS. La communication à l'intérieur du VPC se poursuit soit en HTTP/2 clair sécurisé, soit via un **mTLS** (mutual TLS) géré par un Service Mesh (Istio, Linkerd).
2. **Rate Limiting Distribué :** Algorithme de *Token Bucket* adossé à un cluster Redis pour limiter le débit par utilisateur ou clé d'API (`X-RateLimit-Remaining`).
3. **Circuit Breaker :** Si le service de paiement aval échoue à 50 % sur les 10 dernières secondes, le disjoncteur s'ouvre immédiatement et renvoie un fallback sans saturer le service moribond.

## 3. Middleware Applicatif & Observabilité

La requête atteint enfin le runtime applicatif (ici une application TypeScript / Node.js). 

> [!IMPORTANT]
> Un serveur de production ne commence jamais par exécuter la logique métier. Il applique une série de middlewares stricts pour garantir l'intégrité, la sécurité et la traçabilité.

### Pipeline de Middlewares en TypeScript Strict

```typescript
import { NextFunction, Request, Response } from 'express';
import { z, ZodSchema } from 'zod';
import { randomUUID } from 'node:crypto';

// Extension de typage express sans jamais utiliser 'any'
export interface AuthenticatedUser {
  readonly id: string;
  readonly organizationId: string;
  readonly role: 'ADMIN' | 'MEMBER' | 'VIEWER';
}

export interface AppRequestContext {
  readonly correlationId: string;
  readonly startTime: bigint;
  readonly user?: AuthenticatedUser;
}

export interface SecureRequest<TBody = unknown> extends Request {
  context: AppRequestContext;
  validatedBody?: TBody;
}

// 1. Middleware de Traçabilité OpenTelemetry W3C
export function tracingMiddleware(
  req: Request,
  res: Response,
  next: NextFunction
): void {
  const correlationId = (req.header('x-correlation-id') ?? randomUUID()) as string;
  const secureReq = req as SecureRequest;

  secureReq.context = {
    correlationId,
    startTime: process.hrtime.bigint(),
  };

  res.setHeader('x-correlation-id', correlationId);

  res.on('finish', () => {
    const elapsedMs = Number(process.hrtime.bigint() - secureReq.context.startTime) / 1_000_000;
    // Télémétrie structurée : pas de console.log brut
    if (elapsedMs > 500) {
      // Signaler une alerte de slow request au système APM
    }
  });

  next();
}

// 2. Validation de Schéma Zero-Trust avec Zod
export function validateBody<T>(schema: ZodSchema<T>) {
  return (req: Request, res: Response, next: NextFunction): void => {
    const parseResult = schema.safeParse(req.body);

    if (!parseResult.success) {
      res.status(400).json({
        error: 'VALIDATION_FAILED',
        details: parseResult.error.flatten().fieldErrors,
      });
      return;
    }

    (req as SecureRequest<T>).validatedBody = parseResult.data;
    next();
  };
}
```

## 4. La Couche Métier (Clean Architecture & Domaine Pur)

Une fois validée et contextualisée, la requête entre dans la logique métier pure :

```txt
[ CONTROLLER ] (Désérialise HTTP, adapte au domaine)
       │
       ▼
[ APPLICATION USE CASE ] (Orchestre les transactions, droits, caches)
       │
       ├──> [ DOMAIN ENTITY ] (Règles métier pures, invariants)
       ├──> [ CACHE REPOSITORY ] (Redis Cache-Aside)
       └──> [ DATABASE REPOSITORY ] (Persistance SQL)
```

La couche métier ne dépend d'aucun framework HTTP ni d'aucun ORM spécifique. Si vous remplacez Express par Fastify ou PostgreSQL par MySQL, vos entités métier ne subissent aucune modification.

## 5. Persistance, Caching & Pool de Connexions

C'est ici que 80 % des goulets d'étranglement de latence se produisent en production.

```typescript
// Pattern Cache-Aside avec Redis & PostgreSQL
export class OrderService {
  constructor(
    private readonly cache: CacheRepository,
    private readonly orderRepo: OrderRepository,
    private readonly eventBus: EventPublisher
  ) {}

  public async getOrderById(orderId: string, orgId: string): Promise<OrderDto> {
    const cacheKey = `org:${orgId}:order:${orderId}`;

    // 1. Lecture dans le cache mémoire ultra-rapide (Redis, ~1ms)
    const cached = await this.cache.get<OrderDto>(cacheKey);
    if (cached !== null) {
      return cached;
    }

    // 2. Fallback SQL avec pool de connexion maîtrisé (~10-25ms)
    const order = await this.orderRepo.findUnique(orderId, orgId);
    if (!order) {
      throw new ResourceNotFoundError(`Order ${orderId} not found`);
    }

    const dto = this.mapToDto(order);

    // 3. Réchauffement asynchrone du cache avec TTL
    await this.cache.set(cacheKey, dto, { ttlSeconds: 300 });

    return dto;
  }
}
```

### Le Rôle Vital du Connection Pooling (PgBouncer)
Ouvrir une connexion TCP vers PostgreSQL coûte entre **30 et 100 ms** (fork de processus côté serveur PostgreSQL, allocation mémoire de `work_mem`). 

Sans pool de connexions mandataire comme **PgBouncer**, 500 requêtes concurrentes créent 500 processus sur la base de données, saturant la RAM et provoquant des crashs en cascade (OOM Killer). Le pool maintient un ensemble restreint de connexions persistantes réutilisables instantanément.

## 6. L'Écriture Asynchrone : Transactional Outbox Pattern

Lors d'une mutation (ex: création d'une commande), le client ne doit pas attendre l'envoi du mail de confirmation ni la synchronisation avec le logiciel de comptabilité.

```txt
┌────────────────────────────────────────────────────────┐
│             TRANSACTION SQL UNIQUE (ACID)              │
│                                                        │
│  1. INSERT INTO "orders" (...)                         │
│  2. INSERT INTO "outbox_events" (event, payload, ...)  │
└────────────────────────────────────────────────────────┘
                           │
                           ▼ (Lecture CDC / Debezium)
            [ KAFKA / RABBITMQ MESSAGE BROKER ]
                           │
          ┌────────────────┴────────────────┐
          ▼                                 ▼
   [ Service Email ]               [ Service Facturation ]
```

En écrivant l'événement directement dans une table `outbox_events` dans la même transaction que la commande, vous garantissez la **consistance à deux phases** sans risque de perte de message si le broker réseau est temporairement indisponible.

## Résumé du Cycle de Vie d'une Requête

| Étape | Acteur | Rôle Principal | Latence Typique |
| :--- | :--- | :--- | :--- |
| **1. DNS & TLS** | Edge / CDN | Résolution Anycast & Handshake TLS 1.3 | 20 - 60 ms (initial) |
| **2. Filtrage** | WAF & DDoS Shield | Blocage d'injections et bots malveillants | 2 - 5 ms |
| **3. Ingress** | API Gateway | Rate Limiting, auth JWT, terminaison SSL | 3 - 8 ms |
| **4. Middleware** | Runtime App | Validation Zod, injection du Tracing W3C | 1 - 3 ms |
| **5. Caching** | Redis Cluster | Cache-Aside pour éviter l'accès disque | 1 - 2 ms |
| **6. Persistance** | PgBouncer / Postgres | Transaction ACID, verrous de lignes | 5 - 25 ms |
| **7. Événements** | Outbox -> Kafka | Dispatch asynchrone hors chemin critique | Non-bloquant (0 ms) |

Comprendre cette cascade d'étapes permet d'identifier immédiatement l'origine d'un pic de latence en lisant un diagramme de trace distribuée (**Flamegraph**) et d'architecturer des systèmes capables d'encaisser des centaines de milliers de requêtes par seconde sans fléchir.
