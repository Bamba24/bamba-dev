# Les 5 Principes SOLID Expliqués Simplement : Analogies du Monde Réel et Code TypeScript

Dans les entretiens techniques et les discussions d'architecture logicielle, l'acronyme **SOLID** est mentionné comme le graal absolu de la conception orientée objet. Pourtant, pour beaucoup de développeurs, ces cinq principes restent des concepts abstraits, intimidants et remplis de jargon académique.

Popularisés par Robert C. Martin (*Uncle Bob*) au début des années 2000, les principes SOLID ne sont pas des règles dogmatiques, mais **des remèdes contre la pourriture du code (*Code Rot*)**. Ils empêchent votre application de devenir fragile, rigide et impossible à tester.

Voici le guide complet pour enfin comprendre et appliquer SOLID au quotidien, illustré par des **analogies simples du monde réel** et du code **TypeScript avant / après**.

## 1. 🔪 S — Single Responsibility Principle (SRP)

> **Principe :** Une classe ou un module ne doit avoir qu'une seule et unique raison de changer.

### L'Analogie du Monde Réel
> **L'Analogie du Couteau Suisse :** Un couteau suisse contient une lame, un tire-bouchon, une paire de ciseaux et une scie. C'est pratique en camping, mais dans la cuisine d'un grand restaurant, aucun chef n'utilise un couteau suisse pour découper du saumon ou couper une pizza. Si la lame se casse, tout le couteau doit être envoyé en réparation, privant le cuisinier de ses ciseaux et de son tire-bouchon. Chaque outil doit avoir une tâche unique et la faire à la perfection.

### En Code TypeScript

#### ❌ Avant : La Classe « Homme à Tout Faire » (Violation du SRP)
Cette classe gère à la fois l'authentification, l'écriture en base de données, l'envoi d'emails et la génération de logs :

```typescript
// ❌ CETTE CLASSE A 4 RAISONS DE CHANGER
class UserManager {
  async registerUser(email: string, password: string) {
    // 1. Validation métier
    if (!email.includes("@")) throw new Error("Email invalide");

    // 2. Persistance en BDD
    const user = await db.user.create({ data: { email, password } });

    // 3. Envoi de l'email de bienvenue
    const mailClient = new SmtpClient();
    await mailClient.send(email, "Bienvenue sur notre plateforme !");

    // 4. Écriture dans les logs système
    fs.appendFileSync("server.log", `User registered: ${email}`);
  }
}
```
*Problème :* Si vous changez de fournisseur d'emails (ex: SendGrid vers Resend), vous devez modifier `UserManager`. Si vous modifiez le format de vos logs, vous devez modifier `UserManager`. Le risque de casser l'inscription est permanent.

#### ✅ Après : Responsabilités Séparées
Découpage en trois collaborateurs spécialisés :

```typescript
// 1. Uniquement la persistance
class UserRepository {
  async save(user: UserData) {
    return db.user.create({ data: user });
  }
}

// 2. Uniquement la communication externe
class EmailNotificationService {
  async sendWelcomeEmail(email: string) {
    await emailProvider.send(email, "Bienvenue !");
  }
}

// 3. Le chef d'orchestre métier pur
class UserRegistrationUseCase {
  constructor(
    private userRepo: UserRepository,
    private emailService: EmailNotificationService
  ) {}

  async execute(email: string, passwordHash: string) {
    const user = await this.userRepo.save({ email, passwordHash });
    await this.emailService.sendWelcomeEmail(email);
    return user;
  }
}
```

## 2. 🔌 O — Open / Closed Principle (OCP)

> **Principe :** Une entité logicielle doit être **ouverte à l'extension**, mais **fermée à la modification**.

### L'Analogie du Monde Réel
> **L'Analogie de la Prise Électrique Murale :** Lorsque vous achetez un nouvel aspirateur ou une nouvelle console de jeux, vous ne cassez pas le mur de votre maison pour souder les fils de votre appareil directement aux câbles du disjoncteur. La prise murale est **fermée à la modification** (son câblage ne bouge jamais), mais **ouverte à l'extension** (n'importe quel appareil respectant la norme standard peut s'y brancher).

### En Code TypeScript

#### ❌ Avant : Le `switch-case` qui grandit à l'infini (Violation de l'OCP)
Chaque fois qu'un nouveau moyen de paiement est ajouté, il faut modifier la classe existante :

```typescript
// ❌ IL FAUT RÉOUVRIR CETTE CLASSE À CHAQUE NOUVEAU MOYEN DE PAIEMENT
class PaymentProcessor {
  processPayment(amount: number, method: string) {
    if (method === "STRIPE") {
      stripe.charge(amount);
    } else if (method === "PAYPAL") {
      paypal.sendPayment(amount);
    } else if (method === "WAVE") {
      wave.transfer(amount);
    }
    // Demain : Orange Money ? Crypto ? Il faudra encore modifier cette classe !
  }
}
```

#### ✅ Après : Extension par Contrat d'Interface
On fige le mécanisme d'appel via une interface, et on ajoute de nouveaux modules sans jamais modifier le code déjà testé :

```typescript
// Le contrat stable et fermé
interface PaymentGateway {
  charge(amount: number): Promise<void>;
}

// Extensions indépendantes
class StripePayment implements PaymentGateway {
  async charge(amount: number) { /* appel Stripe */ }
}

class WavePayment implements PaymentGateway {
  async charge(amount: number) { /* appel Wave */ }
}

// Le processeur est désormais TOTALEMENT FERMÉ aux modifications !
class CheckoutService {
  async process(gateway: PaymentGateway, amount: number) {
    await gateway.charge(amount);
  }
}
```

## 3. 🦆 L — Liskov Substitution Principle (LSP)

> **Principe :** Si une classe $S$ est une sous-classe d'une classe $T$, alors tout objet de type $T$ doit pouvoir être remplacé par un objet de type $S$ sans que le programme ne plante ni ne se comporte de façon anormale.

### L'Analogie du Monde Réel
> **L'Analogie du Canard en Plastique :** « Si ça ressemble à un canard, que ça nage comme un canard et que ça fait coin-coin, mais que ça a besoin de piles pour fonctionner... alors vous n'avez pas un vrai canard ! ». Si votre classe enfant hérite d'une classe parent mais lève une exception sur l'une de ses méthodes essentielles, vous violez le principe de substitution.

### En Code TypeScript

#### ❌ Avant : Le Casse-Tête du Carré et du Rectangle (Violation du LSP)
En mathématiques, un carré est un rectangle. Mais en programmation objet, les faire hériter l'un de l'autre conduit à une catastrophe :

```typescript
class Rectangle {
  constructor(protected width: number, protected height: number) {}

  setWidth(w: number) { this.width = w; }
  setHeight(h: number) { this.height = h; }
  getArea(): number { return this.width * this.height; }
}

// ❌ LE CARRÉ BRISE LE COMPORTEMENT ATTENDU DU RECTANGLE
class Square extends Rectangle {
  setWidth(w: number) {
    this.width = w;
    this.height = w; // Force les deux côtés à rester égaux !
  }
  setHeight(h: number) {
    this.width = h;
    this.height = h;
  }
}

function resize(rect: Rectangle) {
  rect.setWidth(5);
  rect.setHeight(4);
  // Pour un Rectangle, 5 * 4 = 20.
  // Mais si on passe un Square, l'aire vaut 16 ! Le contrat est violé !
  console.assert(rect.getArea() === 20, "Échec : Liskov est brisé !");
}
```

#### ✅ Après : Extraire une Abstraction Commune Fiable
Un carré et un rectangle sont tous deux des formes géométriques ayant une aire, mais ils n'ont pas la même règle de mutation :

```typescript
interface Shape {
  getArea(): number;
}

class Rectangle implements Shape {
  constructor(private width: number, private height: number) {}
  getArea() { return this.width * this.height; }
}

class Square implements Shape {
  constructor(private side: number) {}
  getArea() { return this.side * this.side; }
}
```

## 4. 🎛️ I — Interface Segregation Principle (ISP)

> **Principe :** Un client ne doit jamais être forcé d'implémenter des méthodes dont il n'a pas l'utilité. Mieux vaut plusieurs petites interfaces spécifiques qu'une seule interface obèse.

### L'Analogie du Monde Réel
> **L'Analogie de la Télécommande TV :** Imaginez une télécommande universelle monstrueuse comportant 150 boutons : régler la climatisation, ouvrir le garage, piloter un drone, changer de chaîne. Pour allumer votre télévision, vous devez vous trimballer un pavé de 2 kilos avec 140 boutons inutiles. Il est infiniment plus judicieux d'avoir une télécommande dédiée à la télé, et une télécommande dédiée au garage.

### En Code TypeScript

#### ❌ Avant : L'Interface « Obèse » (Violation de l'ISP)

```typescript
// ❌ INTERFACE FOURRE-TOUT TROP LARGE
interface WorkerContract {
  code(): void;
  attendMeetings(): void;
  eatLunch(): void;
  sleep(): void;
}

// Un développeur humain peut tout implémenter :
class HumanDeveloper implements WorkerContract {
  code() { /* code */ }
  attendMeetings() { /* réunion */ }
  eatLunch() { /* pause déjeuner */ }
  sleep() { /* sieste */ }
}

// Mais que se passe-t-il si l'on crée un Agent IA ou un Robot ?
class AiCodingAgent implements WorkerContract {
  code() { /* génère du code */ }
  attendMeetings() { /* non applicable */ }
  eatLunch() { throw new Error("Les robots ne mangent pas !"); } // ⚠️ Méthode forcée absurde
  sleep() { throw new Error("Les robots ne dorment pas !"); }
}
```

#### ✅ Après : Interfaces Ségréguées et Atomiques
On découpe le contrat en rôles ciblés :

```typescript
interface Codeable {
  code(): void;
}

interface Meetable {
  attendMeetings(): void;
}

// L'IA n'implémente que ce qui a du sens pour elle
class AiCodingAgent implements Codeable {
  code() {
    console.log("Génération de code en cours...");
  }
}

// L'humain compose les interfaces dont il a besoin
class HumanEngineer implements Codeable, Meetable {
  code() { /* ... */ }
  attendMeetings() { /* ... */ }
}
```

## 5. 🧱 D — Dependency Inversion Principle (DIP)

> **Principe :**
> 1. Les modules de haut niveau (le cœur métier) ne doivent pas dépendre des modules de bas niveau (les détails techniques comme la BDD ou le réseau). Les deux doivent dépendre d'abstractions.
> 2. Les abstractions ne doivent pas dépendre des détails. Les détails doivent dépendre des abstractions.

### L'Analogie du Monde Réel
> **L'Analogie de la Lampe de Chevet :** Imaginez que pour faire fonctionner une lampe de chevet, vous deviez souder ses fils en cuivre directement sur le réseau électrique de votre fournisseur d'énergie. Si vous voulez changer de lampe ou déménager, vous devez appeler un électricien pour couper le courant dans toute la rue. Grâce à la prise murale standardisée (l'abstraction), la lampe et le réseau électrique sont complètement découplés.

### En Code TypeScript

#### ❌ Avant : Couplage Fort avec une Technologie Concrète (Violation du DIP)
Le service de commandes instancie directement un pilote de base de données MySQL :

```typescript
import { MySQLDriver } from "./drivers/MySQLDriver"; // Dépendance directe vers le bas niveau !

// ❌ CE SERVICE HAUT NIVEAU EST PIÉGÉ PAR MYSQL
class OrderService {
  private db: MySQLDriver;

  constructor() {
    // Couplage dur : impossible de tester avec une BDD en mémoire ou de migrer sur PostgreSQL
    this.db = new MySQLDriver("localhost:3306");
  }

  async createOrder(item: string) {
    await this.db.query(`INSERT INTO orders VALUES ('${item}')`);
  }
}
```

#### ✅ Après : Injection de Dépendance via Abstraction
Le service métier ne connaît qu'une interface. C'est l'extérieur qui lui injecte l'implémentation concrète :

```typescript
// L'abstraction (définit par le haut niveau)
interface OrderRepository {
  save(item: string): Promise<void>;
}

// Le service dépend UNIQUEMENT de l'interface
class OrderService {
  constructor(private orderRepo: OrderRepository) {}

  async createOrder(item: string) {
    await this.orderRepo.save(item);
  }
}

// L'implémentation concrète (détail technique de bas niveau)
class PostgresOrderRepository implements OrderRepository {
  async save(item: string) {
    await pgClient.query("INSERT INTO orders ($1)", [item]);
  }
}

// Pour les tests unitaires : un mock instantané sans base de données !
class InMemoryOrderRepository implements OrderRepository {
  public items: string[] = [];
  async save(item: string) {
    this.items.push(item);
  }
}
```

## 📊 Résumé Mémotechnique des 5 Principes

| Lettre | Nom du Principe | Analogie Clé | Règle d'Or |
| :---: | :--- | :--- | :--- |
| **S** | **Single Responsibility** | Le Couteau Suisse | Une classe = un seul travail bien fait. |
| **O** | **Open / Closed** | La Prise Murale | Nouveaux comportements par ajout de code, pas par modification du code existant. |
| **L** | **Liskov Substitution** | Le Canard en Plastique | Une sous-classe doit honorer le contrat de sa classe parent sans exceptions bizarres. |
| **I** | **Interface Segregation** | La Télécommande TV | Divisez les grosses interfaces en contrats fins et modulaires. |
| **D** | **Dependency Inversion** | La Prise Électrique | Injectez des interfaces, n'instanciez jamais vos dépendances techniques en dur. |
