JavaScript est qualifié de langage **mono-thread synchrone non-bloquant**. Cette description peut sembler paradoxale : comment un moteur d'exécution qui ne dispose que d'un seul thread de calcul principal peut-il traiter des milliers de requêtes réseau, réagir aux clics de l'utilisateur, animer l'interface à 60 FPS et exécuter des opérations asynchrones sans geler ?

La clé de voûte de cette architecture repose sur l'interaction entre le moteur JavaScript (comme **V8** dans Chrome et Node.js), les APIs de l'hôte (Web APIs dans le navigateur ou **libuv** dans Node.js), et surtout : **l'Event Loop** (la boucle d'événements).

Dans cet article d'ingénierie, nous allons décortiquer chaque brique de ce système avec des simulations d'exécution pas à pas et des cas pratiques de production.

## 1. L'Anatomie du Moteur d'Exécution

Pour appréhender l'Event Loop, il faut d'abord visualiser l'espace mémoire d'un runtime JavaScript :

```txt
┌──────────────────────────────────────────────────────────────┐
│                    JavaScript Runtime (V8)                   │
│                                                              │
│  ┌──────────────────────────┐    ┌─────────────────────────┐ │
│  │       Memory Heap        │    │       Call Stack        │ │
│  │   (Allocation mémoire:   │    │    (LIFO: Exécution     │ │
│  │    objets, closures)     │    │   synchrone des frames) │ │
│  └──────────────────────────┘    └─────────────────────────┘ │
└──────────────────────────────┬───────────────────────────────┘
                               │ Appel asynchrone (ex: fetch, setTimeout)
                               ▼
┌──────────────────────────────────────────────────────────────┐
│           Environnement Hôte (Web APIs / libuv)              │
│       Threads d'arrière-plan : Réseau, Timers, I/O disque    │
└──────────────────────────────┬───────────────────────────────┘
                               │ La tâche est prête (callback prêt)
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                 Files d'Attente (Queues)                     │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ Microtask Queue (Promises, queueMicrotask, MutationObs)│  │
│  └────────────────────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ Macrotask Queue (setTimeout, setInterval, I/O, UI)     │  │
│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────────┬───────────────────────────────┘
                               │ Event Loop :
                               │ Pousse dans la Call Stack quand vide
                               ▼
                        [ Call Stack ]
```

### La Call Stack (Pile d'Appels)
La Call Stack est une structure de données **LIFO** (*Last In, First Out*). Dès qu'une fonction est invoquée, une nouvelle *stack frame* (contenant ses arguments et ses variables locales) est empilée au sommet. Dès que la fonction retourne une valeur, sa frame est dépilée.

```typescript
function calculerTVA(prix: number): number {
  return prix * 0.20;
}

function genererFacture(article: string, prix: number): void {
  const tva = calculerTVA(prix);
  console.log(`Article: ${article} | Total TTC: ${prix + tva}€`);
}

genererFacture("Clavier mécanique", 150);
```

Si une fonction s'appelle elle-même indéfiniment sans condition d'arrêt, la mémoire allouée à la pile s'épuise, déclenchant l'erreur redoutée : `RangeError: Maximum call stack size exceeded`.

### Le Memory Heap (Tas Mémoire)
Zone mémoire non structurée où sont alloués les objets, tableaux, closures et fonctions. Le Garbage Collector (GC) surveille périodiquement cette zone pour libérer la mémoire des objets devenus inaccessibles depuis les racines (*GC Roots*).

## 2. Microtasks vs Macrotasks : Les Deux Règles d'Or

L'erreur la plus fréquente chez les développeurs consiste à penser que tous les callbacks asynchrones sont traités au même niveau de priorité. C'est faux : JavaScript possède deux files d'attente distinctes aux règles d'ordonnancement strictes :

| Critère | Microtasks Queue (Jobs) | Macrotasks Queue (Tasks) |
| :--- | :--- | :--- |
| **Origine des tâches** | `Promise` (`.then`, `.catch`, `.finally`), `queueMicrotask()`, `MutationObserver` | `setTimeout`, `setInterval`, `setImmediate` (Node), I/O réseau, événements DOM |
| **Priorité d'exécution** | **Haute priorité immédiate** : Vidée intégralement dès que la Call Stack est vide | **Basse priorité** : Une seule tâche exécutée par tour de boucle (*tick*) |
| **Impact sur le rendu** | Bloque le rendu graphique tant que la file n'est pas totalement vide | Cède la main au moteur de rendu entre deux tâches |

<Note>
**Règle d'or de l'Event Loop** : Dès que la Call Stack se vide, l'Event Loop traite **toutes** les microtâches en attente, jusqu'à épuisement total de la file (y compris les nouvelles microtâches créées pendant cette phase), **avant** de sélectionner la prochaine macrotâche ou de déclencher un rafraîchissement d'écran.
</Note>

## 3. Simulation Pas à Pas : Le Cas Piège d'Entretien

Examinons ce cas classique d'ordonnancement. Quel sera l'ordre d'affichage exact dans la console ?

```typescript
console.log('1: Synchrone');

setTimeout(() => {
  console.log('2: Macrotask (setTimeout 0)');
  Promise.resolve().then(() => {
    console.log('3: Microtask imbriquée dans le setTimeout');
  });
}, 0);

Promise.resolve().then(() => {
  console.log('4: Microtask 1');
}).then(() => {
  console.log('5: Microtask 2');
});

queueMicrotask(() => {
  console.log('6: Microtask explicite');
});

console.log('7: Fin synchrone');
```

### Décorticage de l'exécution :
1. `console.log('1: Synchrone')` s'exécute immédiatement. -> **Affiche 1**.
2. `setTimeout(..., 0)` enregistre un timer dans les Web APIs. Dès 0ms, son callback est placé dans la **Macrotask Queue**.
3. `Promise.resolve().then(...)` place le callback de `Microtask 1` dans la **Microtask Queue**.
4. `queueMicrotask(...)` place le callback de `Microtask explicite` dans la **Microtask Queue**.
5. `console.log('7: Fin synchrone')` s'exécute. -> **Affiche 7**.
6. **La Call Stack est désormais vide**. L'Event Loop inspecte en priorité la **Microtask Queue** :
   - Exécute `Microtask 1` -> **Affiche 4**, qui résout et enregistre `Microtask 2` dans la Microtask Queue.
   - Exécute `Microtask explicite` -> **Affiche 6**.
   - La Microtask Queue contient encore `Microtask 2` : elle l'exécute -> **Affiche 5**.
7. La Microtask Queue est maintenant totalement vide.
8. L'Event Loop passe à la **Macrotask Queue** :
   - Dépile le callback du timer -> **Affiche 2**.
   - Enregistre une nouvelle promesse dans la Microtask Queue.
   - La macrotâche se termine. Avant de continuer, l'Event Loop vide la Microtask Queue -> **Affiche 3**.

**Sortie console finale :**
```txt
1: Synchrone
7: Fin synchrone
4: Microtask 1
6: Microtask explicite
5: Microtask 2
2: Macrotask (setTimeout 0)
3: Microtask imbriquée dans le setTimeout
```

## 4. Navigateur vs Node.js : Ce qui Change Sous le Capot

Si le comportement des promesses est standardisé par la spécification ECMAScript, l'implémentation de la boucle d'événements diffère entre le navigateur et le serveur :

### Dans le Navigateur : La Phase de Rendu
Dans un navigateur, l'Event Loop est synchronisée avec le taux de rafraîchissement de l'écran (généralement 60Hz ou 120Hz, soit une frame toutes les 16.6ms).
- Après l'épuisement des microtâches, le navigateur évalue s'il doit rafraîchir l'écran.
- Il déclenche alors les callbacks enregistrés via `requestAnimationFrame()`, puis exécute les phases de **Style**, **Layout** (calcul géométrique) et **Paint** (rendu graphique des pixels).
- Si une tâche synchrone ou une boucle infinie de microtâches accapare la Call Stack pendant plus de 16ms, l'écran ne peut pas se rafraîchir : l'interface saccade et freeze (*jank*).

### Dans Node.js : Les Phases de libuv
Node.js ne dispose pas de DOM ni d'écran. Sa boucle d'événements est fournie par la bibliothèque C **libuv** et se découpe en phases circulaires distinctes :

```txt
┌────────────────────────────────────────┐
│               timers                   │ ◄── Exécute les callbacks de setTimeout/setInterval
└──────────────────┬─────────────────────┘
                   ▼
┌────────────────────────────────────────┐
│            pending callbacks           │ ◄── Erreurs I/O système différées
└──────────────────┬─────────────────────┘
                   ▼
┌────────────────────────────────────────┐
│             idle, prepare              │ ◄── Usage interne du runtime Node.js
└──────────────────┬─────────────────────┘
                   ▼
┌────────────────────────────────────────┐
│                 poll                   │ ◄── Récupère les nouveaux événements I/O (réseau, disque)
└──────────────────┬─────────────────────┘
                   ▼
┌────────────────────────────────────────┐
│                check                   │ ◄── Exécute les callbacks de setImmediate()
└──────────────────┬─────────────────────┘
                   ▼
┌────────────────────────────────────────┐
│            close callbacks             │ ◄── Fermeture de sockets (socket.on('close'))
└────────────────────────────────────────┘
```

Node.js introduit également `process.nextTick()`. Les callbacks enregistrés par `nextTick` sont stockés dans une file prioritaire (`nextTickQueue`) qui passe **avant** les microtâches de promesses à chaque transition de phase !

## 5. Comment Éviter de Bloquer le Thread Principal

Puisque le thread principal est partagé entre l'exécution de votre logique JavaScript et la réactivité de l'application, tout calcul lourd synchrone paralyse votre système.

### Le Piège de la Famine (*Starvation*)
Créer des microtâches en continu de façon récursive empêche l'Event Loop d'atteindre la phase de rendu ou les macrotâches :

```typescript
// ❌ ANTI-PATTERN : Bloque indéfiniment la machine
function boucleInfinieMicrotasks() {
  Promise.resolve().then(boucleInfinieMicrotasks);
}
```

### Solution 1 : Le Découpage Coopératif (Time Slicing)
Pour traiter de volumineux jeux de données sans bloquer l'UI, découpez le travail en morceaux et cédez la main à l'Event Loop entre chaque lot :

```typescript
async function traiterGrosVolumeEnLots<T>(
  elements: T[],
  tailleLot: number,
  action: (item: T) => void
): Promise<void> {
  for (let i = 0; i < elements.length; i += tailleLot) {
    const lot = elements.slice(i, i + tailleLot);
    lot.forEach(action);

    // Cède la main à l'Event Loop pour le rendu et les événements utilisateurs
    await new Promise((resolve) => setTimeout(resolve, 0));
  }
}
```

### Solution 2 : Déléguer aux Web Workers (ou Worker Threads)
Pour les opérations mathématiques lourdes, la compression d'image, ou le parsing de fichiers volumineux, isolez le traitement sur un thread dédié :

```typescript
// main.ts
const worker = new Worker(new URL('./crypto-worker.ts', import.meta.url));

worker.postMessage({ buffer: largeDataBuffer });
worker.onmessage = (event) => {
  console.log('Résultat calculé en arrière-plan sans bloquer l\'UI :', event.data);
};
```

## Conclusion

L'Event Loop n'est pas une boîte noire magique : c'est un ordonnanceur rigoureux réggi par des priorités prévisibles. En maîtrisant la distinction entre la Call Stack, la file de Microtâches ultra-prioritaire et la file de Macrotâches, vous êtes armé pour diagnostiquer les freezes d'interface, optimiser les performances de vos serveurs Node.js et écrire du code asynchrone robuste et performant.
