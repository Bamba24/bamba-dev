# Le Voyage d'une Requête Web : De l'Écran du Smartphone au Disque Dur de la Base de Données

Imaginez un patient sur son smartphone. Il consulte l'application de son cabinet médical et appuie sur son écran tactile :

> **« Confirmer mon rendez-vous avec le Dr. Dupont pour mardi à 14h00 »**

En moins de **120 millisecondes**, l'écran s'illumine d'une coche verte confirmant la réservation.

Pour l'utilisateur, ce geste semble anodin et instantané. Pourtant, sous le capot, des millions d'électrons ont traversé des câbles de fibre optique sous-marins, franchi des protocoles cryptographiques inviolables, sollicité des serveurs mandataires et déclenché des mécanismes transactionnels complexes sur les disques durs d'un cluster PostgreSQL.

Dans cette masterclass d'ingénierie logicielle, nous allons décortiquer pas à pas, milliseconde par milliseconde, **les 10 étapes invisibles du grand voyage d'une requête web**.

## ACTE 1 : Le Grand Voyage Réseau (Du navigateur au serveur)

### Étape 1 : Le DNS — « Trouver où habite le serveur » 🗺️

Le smartphone du patient sait qu'il doit envoyer les données à l'adresse textuelle `api.cabinet-medical.fr`.

Problème : les routeurs physiques d'Internet ne comprennent pas les noms de domaine en français ou en anglais. Ils ne savent router des paquets d'octets que vers des **adresses IP numériques** (ex: `51.159.23.4`).

Le smartphone consulte alors le **Domain Name System (DNS)**, l'annuaire universel et distribué d'Internet :

1. **Cache local** : Le système vérifie si l'adresse est déjà en mémoire dans le smartphone ou la box Wi-Fi.
2. **Requête récursive** : Si elle est inconnue, le smartphone interroge le résolveur DNS de son opérateur :
   - Le résolveur interroge les serveurs racine (*Root Servers* `.`).
   - Il est aiguillé vers les serveurs du registre national (`.fr`).
   - Il interroge enfin le serveur de noms faisant autorité (*Authoritative DNS*, ex: Cloudflare ou AWS Route 53).

```txt
Smartphone ──► « Où se trouve api.cabinet-medical.fr ? »
DNS Server ◄── « Adresse IP trouvée : 51.159.23.4 (TTL = 300s) »
```

⏱️ **Temps écoulé : ~5 à 15 ms** (ou instantané si mis en cache).

---

### Étape 2 : Le Handshake TCP — « La poignée de main » 🤝

Avant de transférer le moindre mot, les deux machines doivent établir un canal de communication fiable et bidirectionnel. C'est le rôle du protocole **TCP (Transmission Control Protocol)**.

Elles exécutent le célèbre **Three-Way Handshake** (poignée de main en trois temps) :

```txt
Smartphone                                            Serveur
    │                                                    │
    │  1. SYN  (« Tu m'entends ? Je veux te parler »)   │
    │ ─────────────────────────────────────────────────► │
    │                                                    │
    │  2. SYN-ACK (« Oui je t'entends, tu m'entends ? »)│
    │ ◄───────────────────────────────────────────────── │
    │                                                    │
    │  3. ACK  (« Parfait, le canal est ouvert ! »)      │
    │ ─────────────────────────────────────────────────► │
```

**Pourquoi TCP est-il indispensable ?**
Contrairement à UDP (utilisé pour le streaming vidéo où perdre une image n'est pas grave), TCP garantit qu'**aucun paquet ne peut être perdu**. Chaque paquet reçoit un numéro de séquence ; si un paquet arrive corrompu ou manquant à cause d'une interférence radio 4G, TCP le réexpédie automatiquement.

⏱️ **Temps écoulé : ~15 à 30 ms** (1 aller-retour réseau / Round Trip Time).

---

### Étape 3 : Le Tunnel TLS / SSL — « Le cadenas secret » 🔒

La liaison TCP est établie, mais elle traverse des relais publics. Si nous envoyions les informations médicales en clair, n'importe quel espion sur le réseau Wi-Fi local pourrait lire l'identité du patient et ses rendez-vous.

Le protocole **TLS 1.3 (Transport Layer Security)** entre en jeu pour verrouiller la communication :

1. **Vérification d'identité** : Le serveur présente son certificat numérique signé par une Autorité de Certification (Let's Encrypt, DigiCert). Le smartphone vérifie cryptographiquement que le serveur est bien le propriétaire légitime de `cabinet-medical.fr`.
2. **Échange de clés éphémères (Diffie-Hellman)** : Sans jamais envoyer le secret sur le réseau, les deux machines génèrent mathématiquement une clé de chiffrement symétrique unique pour cette session.
3. **Chiffrement absolu** : À partir de cette microseconde, chaque octet transmis devient une suite indéchiffrable de caractères aléatoires pour tout observateur extérieur.

⏱️ **Temps écoulé : ~10 à 25 ms**.

---

### Étape 4 : L'Enveloppe HTTP — « Le message formel » ✉️

À l'abri dans le tunnel chiffré, le navigateur glisse la demande du patient dans une enveloppe standardisée : la **requête HTTP**.

```http
POST /api/v1/rendezvous HTTP/1.1
Host: api.cabinet-medical.fr
User-Agent: Mozilla/5.0 (iPhone; CPU iPhone OS 18_1)
Content-Type: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

{
  "medecinId": 12,
  "dateHeure": "2026-10-21T14:00:00Z",
  "motif": "Consultation générale"
}
```

- **Le Verbe (`POST`)** : L'intention métier (créer une nouvelle ressource).
- **Les Headers (En-têtes)** : Les métadonnées de sécurité (token JWT d'authentification) et le format des données.
- **Le Body (Corps)** : Le payload JSON contenant les données réelles du rendez-vous.

---

### Étape 5 : Le Reverse Proxy — « L'agent de sécurité à l'entrée » 🛡️

Le paquet réseau atteint le datacenter. Mais dans une architecture moderne, **aucun serveur d'application (Node.js, Go, Python) n'est exposé directement à Internet**.

La requête est réceptionnée par un **Reverse Proxy / Load Balancer** (Cloudflare, Nginx, Traefik ou Caddy) :

1. **Protection DDoS & WAF** : Le pare-feu applicatif vérifie que l'IP n'est pas blacklistée et qu'il ne s'agit pas d'une attaque par injection SQL.
2. **Terminaison TLS** : Le reverse proxy déchiffre la couche SSL pour décharger le processeur du serveur d'application.
3. **Aiguillage (Load Balancing)** : Si votre backend tourne sur 5 conteneurs ou machines virtuelles, le proxy redirige la requête vers le serveur le moins chargé selon un algorithme *Round Robin* ou *Least Connections*.

⏱️ **Temps écoulé : ~2 à 5 ms**.

## ACTE 2 : La Plongée en Base de Données (Sous le capot du moteur SQL)

Votre serveur backend reçoit la requête HTTP déchiffrée. Après avoir vérifié le token JWT du patient, il doit inscrire la réservation dans la base de données PostgreSQL (hébergée sur Neon, AWS RDS ou Supabase).

C'est ici que commence le cœur de l'ingénierie des données.

---

### Étape 6 : Qu'est-ce qu'une « Connexion BDD » physiquement ? 🔌

Beaucoup de développeurs imaginent qu'une connexion SQL est une simple abstraction virtuelle. En réalité, une connexion à PostgreSQL est un processus lourd :

- C'est un **Socket TCP persistant** ouvert entre votre backend et le port `5432` du serveur SQL.
- Côté PostgreSQL, chaque connexion instancie un **processus Unix dédié** en mémoire RAM qui alloue :
  - Un espace pour les variables de session.
  - La gestion des verrous et de l'état transactionnel.
  - De la mémoire de travail (*work_mem* pour les tris et jointures).

```txt
┌────────────────────────────────────────────────────────┐
│                   LE COÛT D'UNE CONNEXION              │
├────────────────────────────────────────────────────────┤
│ • Temps de négociation réseau + auth : 80 à 150 ms     │
│ • Consommation RAM par connexion : 5 à 10 Mo           │
│                                                        │
│ 💥 CONSÉQUENCE : Si 500 utilisateurs ouvraient une    │
│ connexion brute en même temps, la base exploserait !   │
└────────────────────────────────────────────────────────┘
```

### Étape 7 : Le Connection Pool en action (HikariCP / PgBouncer) 🚕

Pour éviter l'écroulement de la base, le serveur utilise un **Pool de Connexions** :

```txt
Serveur Backend (Pool de 10 connexions permanentes)
  Connexion 1 : [Occupée]
  Connexion 2 : [Occupée]
  Connexion 3 : [LIBRE] ◄── Prêtée immédiatement en 0,2 ms !
  Connexion 4 : [Occupée]
```

1. Au démarrage, l'application pré-ouvre une dizaine de connexions vers la base de données.
2. Lorsque la requête du patient arrive, le serveur demande au pool : *« Prête-moi une connexion disponible ! »*
3. Le pool fournit instantanément la connexion n° 3.
4. Dès que la requête SQL est exécutée, la connexion n'est pas détruite : elle est **restituée au pool**, prête pour le patient suivant.

⏱️ **Temps écoulé : < 1 ms** (au lieu de 120 ms sans pool).

---

### Étape 8 : La Transaction ACID — « Tout ou Rien » ⚖️

Enregistrer un rendez-vous médical ne consiste pas à exécuter une simple ligne SQL isolée. C'est une opération composite :

- **Étape A** : Insérer la ligne dans la table `rendez_vous`.
- **Étape B** : Mettre à jour le créneau horaire dans `disponibilites` pour le passer à `"RESERVE"`.
- **Étape C** : Déduire 1 crédit de consultation du solde du patient.

Que se passe-t-il si le serveur subit une panne de courant ou un crash mémoire pile après l'Étape B ? Le créneau serait bloqué pour toujours sans que le rendez-vous ne soit créé !

Pour garantir l'intégrité absolue, le code enveloppe ces instructions dans une **Transaction ACID** :

```sql
BEGIN TRANSACTION;

-- 1. Création du rendez-vous
INSERT INTO rendez_vous (medecin_id, patient_id, date_heure, status)
VALUES (12, 45, '2026-10-21 14:00:00', 'CONFIRME');

-- 2. Blocage du créneau
UPDATE disponibilites 
SET statut = 'RESERVE' 
WHERE medecin_id = 12 AND date_heure = '2026-10-21 14:00:00';

-- 3. Débit du solde
UPDATE patients 
SET credits_consultation = credits_consultation - 1 
WHERE id = 45;

COMMIT;
```

<Note>
**La promesse de l'Atomicité (ACID) :**
- Si toutes les instructions réussissent ➔ **`COMMIT`** : Les modifications sont écrites définitivement sur le disque dur (*Write-Ahead Logging*).
- Si la moindre erreur survient ➔ **`ROLLBACK`** : PostgreSQL annule l'intégralité des modifications en mémoire comme si rien ne s'était jamais produit. Aucune donnée bancale n'est laissée en base.
</Note>

### Étape 9 : Le Verrou (Lock) & Le Problème de Concurrence 🔐

Voici le cauchemar de tout système de réservation : **deux patients cliquent exactement à la même milliseconde pour réserver le même créneau du Dr. Dupont le mardi à 14h00.**

Comment PostgreSQL empêche-t-il le double rendez-vous ?

Grâce au **Verrouillage de Ligne (Row-Level Locking)** :

```txt
Temps T0 : La transaction du Patient A arrive une nanoseconde avant.
           Elle pose un verrou exclusif sur la ligne du créneau de 14h00.
                │
                ▼
Temps T1 : La transaction du Patient B arrive sur le même créneau.
           PostgreSQL détecte le verrou et met la transaction B en PAUSE.
                │
                ▼
Temps T2 : La transaction du Patient A réussit et valide (COMMIT).
           Le créneau passe au statut 'RESERVE'. Le verrou est libéré.
                │
                ▼
Temps T3 : La transaction du Patient B se réveille, constate que la condition
           "WHERE statut = 'LIBRE'" n'est plus respectée, et échoue proprement.
```

Le Patient B reçoit un message d'erreur ergonomique : *« Ce créneau vient tout juste d'être réservé par un autre utilisateur. »*

---

### Étape 10 : Le Voyage Retour 🏁

1. PostgreSQL inscrit les données dans le journal de transactions (*WAL - Write-Ahead Log*) sur son disque NVMe et confirme au backend : `INSERT 0 1 (id: 104)`.
2. Le backend libère la connexion SQL vers le pool.
3. Le serveur formule une réponse HTTP standardisée :

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "success": true,
  "rendezVousId": 104,
  "message": "Rendez-vous confirmé avec succès pour le mardi à 14h00"
}
```

4. Le paquet HTTP fait le trajet inverse à travers le réseau fibre et 4G jusqu'au smartphone.
5. Le composant React du patient bascule son état et affiche une animation de confirmation :

> **« Votre rendez-vous est confirmé ! »**
