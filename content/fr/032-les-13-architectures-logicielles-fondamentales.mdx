# Les 13 Architectures Logicielles Fondamentales : Guide Complet & Matrice de Décision

Dans le cycle de vie d'un projet informatique, le choix de l'architecture logicielle est sans doute la décision qui aura le plus d'impact sur la longévité, le coût d'exploitation et la vélocité des équipes.

Une architecture logicielle n'est jamais « parfaite » ou « mauvaise » dans l'absolu. Elle incarne un ensemble d'arbitrages et de compromis techniques (*trade-offs*) entre :
- La **simplicité** d'écriture et de déploiement
- La **scalabilité horizontale**
- La **tolérance aux pannes** et la résilience
- La **latence réseau**
- La **taille et l'autonomie des équipes**

Voici le tour d'horizon exhaustif des **13 architectures logicielles incontournables** qui composent l'état de l'art du génie logiciel moderne.

## 1. L'Architecture Monolithique (Classique & Modulaire)

### Le Principe
Dans un **Monolithe Classique**, tous les composants de l'application (l'interface utilisateur ou les contrôleurs d'API, la logique métier, la validation et l'accès à la base de données) sont regroupés dans une unique base de code et compilés/exécutés au sein d'un seul processus système.

Pour pallier le désordre du code à grande échelle, le **Monolithe Modulaire** structure le code en modules fonctionnels indépendants avec des frontières scellées (visibilité restreinte et interfaces publiques d'appels internes).

```txt
┌──────────────────────────────────────────────────────────────┐
│                    PROCESSUS UNIQUE EXÉCUTABLE               │
│                                                              │
│  ┌──────────────────┐  ┌──────────────────┐  ┌────────────┐  │
│  │  Module Commandes│  │  Module Paiement │  │Module Auth │  │
│  └────────┬─────────┘  └────────┬─────────┘  └─────┬──────┘  │
│           └─────────────────────┼──────────────────┘         │
│                                 ▼                            │
│                      Base de Données Unique                  │
└──────────────────────────────────────────────────────────────┘
```

### Forces & Faiblesses
- **Avantages** :
  - Déploiement trivial (un seul conteneur Docker ou binaire à lancer).
  - Latence réseau inter-modules strictement nulle (appels de fonctions directes en mémoire).
  - Transactions ACID natives : rollback immédiat en cas d'erreur sans coordination complexe.
  - Débogage local simple (un seul point d'arrêt dans l'IDE suffit).
- **Inconvénients** :
  - Scalabilité tout-ou-rien : pour encaisser la charge d'un sous-module saturé, il faut dupliquer tout le monolithe en mémoire.
  - Risque d'enchevêtrement progressif du code (le fameux « plat de spaghettis ») si la discipline d'équipe faiblit.
  - Temps de build et de CI qui augmentent avec la taille du code.
- **Cas d'usage recommandés** : Startups, MVPs, 90 % des nouveaux projets SaaS, équipes de moins de 15 développeurs.

## 2. L'Architecture N-Tiers / En Couches (Layered Architecture)

### Le Principe
L'application est découpée horizontalement en couches logiques ayant chacune une responsabilité dédiée. Une couche ne communique généralement qu'avec la couche située immédiatement en dessous d'elle.

```txt
┌──────────────────────────────────────────────────────────┐
│ 1. Couche Présentation (UI, Pages, Contrôleurs API)     │
└────────────────────────────┬─────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────┐
│ 2. Couche Métier / Domaine (Services, Logique métier)    │
└────────────────────────────┬─────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────┐
│ 3. Couche Accès Données / Persistance (Repositories/ORM) │
└────────────────────────────┬─────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────┐
│ 4. Couche Données (PostgreSQL, MySQL, Redis)            │
└──────────────────────────────────────────────────────────┘
```

### Forces & Faiblesses
- **Avantages** :
  - Modèle éprouvé, standardisé dans l'industrie et facile à appréhender pour les juniors.
  - Séparation stricte des préoccupations (*Separation of Concerns*).
- **Inconvénients** :
  - Anti-pattern « Pass-Through » : multiplication de code sans valeur où un contrôleur appelle un service qui se contente d'appeler un repository sans aucune transformation.
  - Couplage vertical rigide : chaque modification d'un champ en base nécessite souvent de modifier 4 couches de code.
- **Cas d'usage recommandés** : Applications de gestion d'entreprise, CRUD traditionnels, frameworks MVC (NestJS, Django, Spring Boot, Laravel).

## 3. L'Architecture Microservices

### Le Principe
L'application est divisée en un ensemble de services autonomes et hautement spécialisés, construits autour de domaines métiers délimités (*Bounded Contexts* selon le DDD). Chaque microservice possède sa propre base de données (*Database-per-Service*) et communique via des APIs HTTP/REST, gRPC ou des messages asynchrones.

```txt
                     ┌──────────────────┐
                     │   API Gateway    │
                     └────────┬─────────┘
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
┌───────────────┐     ┌───────────────┐     ┌───────────────┐
│ Service Auth  │     │ Service Panier│     │Service Facture│
└───────┬───────┘     └───────┬───────┘     └───────┬───────┘
        ▼                     ▼                     ▼
   [BDD Auth]            [BDD Panier]          [BDD Facture]
```

### Forces & Faiblesses
- **Avantages** :
  - Scalabilité granulaire indépendante : allouez 20 instances au service de paiement sans toucher au reste.
  - Autonomie technique : possibilité d'utiliser Go pour la performance réseau et Python pour l'IA dans le même écosystème.
  - Déploiement isolé : déployer une mise à jour sur le panier ne perturbe pas le module d'authentification.
- **Inconvénients** :
  - Fin des transactions ACID universelles : nécessite des patrons de compensation comme la **Saga**.
  - Complexité opérationnelle titanesque (orchestration Kubernetes, service mesh, tracing distribué Jaeger/OpenTelemetry).
  - Consistance éventuelle des données et latence réseau inter-services.
- **Cas d'usage recommandés** : Grandes entreprises technologiques (Amazon, Netflix, Uber) avec plusieurs dizaines d'équipes pluridisciplinaires autonomes.

## 4. L'Architecture Événementielle (Event-Driven Architecture - EDA)

### Le Principe
Au lieu de communiquer par des requêtes directes de type « question-réponse » (HTTP synchrone), les composants émettent des **Événements** décrivant des faits passés (`OrderValidated`, `PaymentReceived`). Ces événements sont publiés dans un courtier (*Message Broker*) et consommés de façon asynchrone par des services abonnés.

```txt
┌───────────────┐  OrderPlaced   ┌──────────────────┐    Consume   ┌────────────────┐
│ Service Order │───────────────►│  Message Broker  │─────────────►│Service Facture │
└───────────────┘                │ (Kafka/RabbitMQ) │              └────────────────┘
                                 └────────┬─────────┘
                                          │             Consume   ┌────────────────┐
                                          └──────────────────────►│ Service Email  │
                                                                  └────────────────┘
```

### Forces & Faiblesses
- **Avantages** :
  - Découplage temporel et spatial complet : si le service d'envoi d'emails plante, le flux de commande n'est pas bloqué ; les messages restent dans la file en attendant son redémarrage.
  - Gestion native de la contre-pression (*Backpressure*) lors des pics de charge.
  - Ajout de nouveaux consommateurs sans modifier aucun producteur.
- **Inconvénients** :
  - Débogage difficile sans observabilité dédiée.
  - Risque de messages dupliqués ou désordonnés (*At-least-once delivery*).
- **Cas d'usage recommandés** : Traitements financiers temps réel, logistique e-commerce, flux télémétriques IoT.

## 5. L'Architecture Hexagonale (Ports et Adaptateurs)

### Le Principe
Théorisée par Alistair Cockburn, l'architecture hexagonale isole complètement le cœur métier pur de tout détail technique externe. Le cœur définit des **Ports** (interfaces d'entrée et de sortie). Les technologies concrètes (PostgreSQL, Stripe, Fastify) sont des **Adaptateurs** qui s'enfichent sur ces ports.

```txt
                 ┌────────────────────────────────┐
                 │      ADAPTATEURS PRIMAIRES     │
                 │   (API REST, CLI, GraphQL)     │
                 └───────────────┬────────────────┘
                                 ▼
                     ┌───────────────────────┐
                     │   Port Entrant (In)   │
                     └───────────┬───────────┘
                                 ▼
                   ┌───────────────────────────┐
                   │       CŒUR MÉTIER         │
                   │    (Entités & Règles)     │
                   └─────────────┬─────────────┘
                                 ▼
                     ┌───────────────────────┐
                     │   Port Sortant (Out)  │
                     └───────────┬───────────┘
                                 ▼
                 ┌────────────────────────────────┐
                 │     ADAPTATEURS SECONDAIRES    │
                 │   (Postgres, Redis, Stripe)    │
                 └────────────────────────────────┘
```

### Forces & Faiblesses
- **Avantages** :
  - Testabilité totale : testez 100 % de votre logique métier avec de faux adaptateurs en mémoire (mocks ultra-simples), sans jamais lancer de base de données.
  - Changement d'infrastructure indolore : remplacer Prisma par Kysely ou Stripe par Adyen ne nécessite de toucher qu'à un adaptateur sans modifier le métier.
- **Inconvénients** :
  - Verbosité initiale : écriture de nombreuses interfaces et conversion constante entre modèles du domaine et DTOs d'infrastructure.
- **Cas d'usage recommandés** : Applications financières, assurances, cœurs de métier complexes avec application rigoureuse du DDD.

## 6. La Clean Architecture (Uncle Bob) & Onion Architecture

### Le Principe
Créée par Robert C. Martin, elle repose sur des cercles concentriques régis par la **Règle de Dépendance** : le code ne peut dépendre que des cercles situés plus à l'intérieur. Les entités d'entreprise sont au centre, protégées des détails de présentation ou de stockage.

```txt
┌────────────────────────────────────────────────────────┐
│  Frameworks & Drivers (Web, DB, Périphériques, UI)     │
│   ┌────────────────────────────────────────────────┐   │
│   │  Interface Adapters (Contrôleurs, Présenteurs) │   │
│   │   ┌────────────────────────────────────────┐   │   │
│   │   │  Application Business Rules (Use Cases)│   │   │
│   │   │   ┌────────────────────────────────┐   │   │   │
│   │   │   │     Enterprise Entities        │   │   │   │
│   │   │   └────────────────────────────────┘   │   │   │
│   │   └────────────────────────────────────────┘   │   │
│   └────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────┘
```

### Forces & Faiblesses
- **Avantages** : Indépendance technologique absolue vis-à-vis des frameworks (React, Express ou NestJS ne sont que des détails interchangeables).
- **Inconvénients** : Forte courbe d'apprentissage et risque d'over-engineering sur les projets à faible logique métier.
- **Cas d'usage recommandés** : Systèmes d'entreprise stratégiques prévus pour durer plus de 10 ans sans réécriture totale.

## 7. CQRS & Event Sourcing (Command Query Responsibility Segregation)

### Le Principe
- **CQRS** sépare explicitement le modèle d'écriture (**Commandes** qui valident et exécutent les changements d'état) du modèle de lecture (**Requêtes** qui interrogent des vues dénormalisées optimisées).
- **Event Sourcing** enregistre l'état du système non pas sous forme d'une table avec l'état actuel (`UPDATE user SET status = 'ACTIVE'`), mais sous forme d'un journal immuable d'événements passés (`UserRegistered`, `EmailVerified`).

```txt
[Client] ──(Commande)──► [Domain Model] ──► [Event Store (Append Only)]
                                                    │
                                              Event Stream
                                                    ▼
[Client] ◄──(Requête)─── [Read Model (Cache/ES)] ◄──┘ (Projection)
```

### Forces & Faiblesses
- **Avantages** : Piste d'audit native infalsifiable, capacité de voyager dans le temps pour reconstruire l'état à n'importe quelle date passée.
- **Inconvénients** : Latence de projection (modèle de lecture asynchrone), complexité extrême de refactorisation des schémas d'événements historiques.
- **Cas d'usage recommandés** : Systèmes bancaires, livres comptables, systèmes de réservation haute concurrence.

## 8. L'Architecture Serverless (FaaS - Function as a Service)

### Le Principe
L'application est découpée en fonctions atomiques sans état (*Stateless*) qui démarrent à la demande en quelques millisecondes lorsqu'un événement survient (requête HTTP, fichier déposé sur S3) et s'arrêtent immédiatement après.

```txt
Requête HTTP ──► [API Gateway] ──► [Lambda Instance (Auto-scale 0 -> N)] ──► [Base Serverless]
```

### Forces & Faiblesses
- **Avantages** : Coût zéro au repos (aucun centime dépensé sans trafic), montée en charge élastique sans aucune gestion de serveurs physiques.
- **Inconvénients** : Problème du démarrage à froid (*Cold Start*), limites d'exécution (timeout max 15 minutes), saturation des pools de connexions SQL classiques sans proxy dédié.
- **Cas d'usage recommandés** : Traitements asynchrones d'images/vidéos, webhooks, tâches cron cloud, APIs à trafic imprévisible.

## 9. L'Architecture Micro-frontends

### Le Principe
Transposition du paradigme des microservices au navigateur web. Une application volumineuse est découpée en micro-applications autonomes détenues par différentes équipes, assemblées au runtime au sein d'une application racine (*App Shell*) grâce à Module Federation ou des Web Components.

```txt
┌────────────────────────────────────────────────────────┐
│                   APPLICATION SHELL                    │
│  ┌──────────────────────┐    ┌──────────────────────┐  │
│  │ Équipe Auth (React)  │    │ Équipe Panier (Vue)  │  │
│  └──────────────────────┘    └──────────────────────┘  │
│  ┌──────────────────────────────────────────────────┐  │
│  │ Équipe Catalogue / Recherche (Next.js / Vanilla) │  │
│  └──────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

### Forces & Faiblesses
- **Avantages** : Déploiements front-end totalement décorrélés sans bloquer les autres équipes, autonomie d'organisation.
- **Inconvénients** : Risque d'explosion de la taille des bundles si les librairies communes ne sont pas partagées, complexité du routage global et du partage d'état.
- **Cas d'usage recommandés** : Très grandes plateformes d'e-commerce et de streaming (Spotify, DAZN, IKEA).

## 10. L'Architecture Orientée Services (SOA)

### Le Principe
Prédécesseur historique des microservices dans les années 2000, la SOA interconnecte des services métiers réutilisables à travers un bus informatique centralisé : l'**ESB** (*Enterprise Service Bus*), chargé de router, transformer (XML/SOAP) et valider les échanges.

```txt
[Client Web]      [App Mobile]      [Partenaire B2B]
      │                 │                  │
      └─────────────────┼──────────────────┘
                        ▼
      ┌──────────────────────────────────┐
      │   ENTERPRISE SERVICE BUS (ESB)   │
      └─────────────────┬────────────────┘
                        ▼
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
     [Module SAP]  [Module CRM]  [Module RH]
```

### Forces & Faiblesses
- **Avantages** : Excellente réutilisation des systèmes patrimoniaux (*legacy*) hétérogènes.
- **Inconvénients** : L'ESB concentre trop de règles métiers et devient un énorme goulot d'étranglement monolithique et fragile (*smart pipes, dumb endpoints*).
- **Cas d'usage recommandés** : Très grandes banques, assurances et administrations publiques modernisant un parc de mainframes.

## 11. L'Architecture Pipe and Filter (Tubes et Filtres)

### Le Principe
Le traitement de données est organisé comme une chaîne d'étapes séquentielles et autonomes (**Filtres**) reliées entre elles par des canaux de flux unidirectionnels (**Pipes**).

```txt
[Source] ──► [Pipe 1] ──► [Filtre Nettoyage] ──► [Pipe 2] ──► [Filtre Chiffrement] ──► [Destination]
```

### Forces & Faiblesses
- **Avantages** : Simplicité conceptuelle, réutilisabilité des filtres dans d'autres pipelines, parallélisation aisée.
- **Inconvénients** : Surcoût de sérialisation/désérialisation entre chaque filtre, gestion complexe des rollbacks en cas d'échec en fin de chaîne.
- **Cas d'usage recommandés** : Pipelines d'ingestion ETL de données, encodage vidéo/audio, compilateurs et transpileurs (Babel, SWC).

---

## 12. L'Architecture Pair-à-Pair (Peer-to-Peer - P2P)

### Le Principe
Réseau décentralisé sans serveur centralisé obligatoire. Chaque nœud participant (*peer*) partage simultanément ses ressources de stockage, de calcul ou de bande passante avec les autres nœuds.

```txt
    [Nœud 1] ◄──────────────► [Nœud 2]
       ▲  ▲                      ▲  ▲
       │  └───────────┐  ┌───────┘  │
       │              ▼  ▼          │
    [Nœud 3] ◄──────────────► [Nœud 4]
```

### Forces & Faiblesses
- **Avantages** : Résilience totale (impossible à faire tomber d'un coup), résistance à la censure, la capacité globale augmente avec chaque nouvel utilisateur.
- **Inconvénients** : Sécurité délicate face aux nœuds malveillants, découverte lente sans DHT (*Distributed Hash Table*).
- **Cas d'usage recommandés** : Blockchains (Bitcoin, Ethereum), protocoles de transfert décentralisé (BitTorrent, IPFS), WebRTC.

## 13. L'Architecture Space-Based (Tuple Space / In-Memory Grid)

### Le Principe
Conçue pour supprimer le verrou de la base de données relationnelle sous un trafic phénoménal. Les données transactionnelles actives sont répliquées et traitées directement dans la RAM d'unités de traitement indépendantes (*Processing Units*), formant une grille mémoire distribuée (*In-Memory Data Grid*). La base de données physique n'est mise à jour qu'en arrière-plan de façon asynchrone.

```txt
                  ┌────────────────────────┐
                  │   Virtual Middleware   │
                  │   (Routage & Session)  │
                  └───────────┬────────────┘
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
┌──────────────────┐ ┌──────────────────┐ ┌──────────────────┐
│ Processing Unit 1│ │ Processing Unit 2│ │ Processing Unit 3│
│ [Code + RAM Grid]│ │ [Code + RAM Grid]│ │ [Code + RAM Grid]│
└────────┬─────────┘ └────────┬─────────┘ └────────┬─────────┘
         └────────────────────┼────────────────────┘
                              ▼ (Persistance Asynchrone)
                     [Base SQL / NoSQL]
```

### Forces & Faiblesses
- **Avantages** : Performances foudroyantes (temps de réponse en microsecondes), scalabilité instantanée face à des pics massifs.
- **Inconvénients** : Coût très élevé en mémoire vive (RAM), complexité pour garantir la synchronisation sans perte en cas de crash brutal.
- **Cas d'usage recommandés** : Trading haute fréquence (HFT), billetteries de concerts géants (vente de 100 000 billets en 15 secondes), jeux vidéo massivement multijoueurs.

| **Microservices** | Très élevée | Illimitée | Élevé | Géants tech, équipes multiples indépendantes |
| **Événementielle (EDA)** | Élevée | Très élevée | Moyen/Élevé | Systèmes réactifs, commandes, IoT |
