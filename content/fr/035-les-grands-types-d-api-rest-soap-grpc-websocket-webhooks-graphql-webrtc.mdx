# Les 7 Types d'APIs et Protocoles de Communication : REST, SOAP, gRPC, WebSocket, Webhooks, GraphQL et WebRTC

Dans le développement logiciel moderne, une application ne vit jamais en vase clos. Elle doit échanger des données avec des navigateurs, des applications mobiles, des microservices internes, des objets connectés ou des services tiers (Stripe, GitHub, Twilio).

Mais comment ces systèmes communiquent-ils ?

Il n'existe pas de solution universelle : faire du chat temps réel en REST relève du calvaire, tout comme utiliser WebRTC pour concevoir un CRUD de base d'utilisateurs. Chaque style d'API et protocole répond à une problématique d'ingénierie précise en faisant des compromis sur **la latence, le format de sérialisation, la bidirectionnalité et la complexité opérationnelle**.

Dans ce guide complet, nous allons explorer en détail les **7 grands types d'APIs et de protocoles de communication** qui dominent l'industrie.

## 1. REST (Representational State Transfer)

Théorisé par Roy Fielding en 2000 dans sa thèse de doctorat, **REST** n'est pas un protocole mais un **style architectural** basé sur les standards du web et le protocole HTTP.

```txt
[Client HTTP] ──── GET /api/v1/users/42 ────► [Serveur REST]
              ◄── 200 OK + JSON Payload ────
```

### Fonctionnement & Principes Clés
- **Centré sur les Ressources** : Chaque entité est identifiée par une URI unique et canonique (ex: `/api/v1/products/123/reviews`).
- **Verbes HTTP sémantiques** :
  - `GET` : Lecture (sûr et idempotent).
  - `POST` : Création de ressource.
  - `PUT` : Remplacement complet d'une ressource (idempotent).
  - `PATCH` : Mise à jour partielle.
  - `DELETE` : Suppression (idempotent).
- **Stateless (Sans État)** : Chaque requête contient toutes les informations nécessaires à son exécution (souvent via un header `Authorization: Bearer <token>`).
- **Mise en cache native** : Exploite directement les en-têtes HTTP (`Cache-Control`, `ETag`, `Last-Modified`) supportés par les navigateurs, proxies et CDNs.
- **HATEOAS** (*Hypermedia As The Engine Of Application State*) : Les réponses fournissent des hyperliens vers les actions suivantes disponibles (rarement implémenté à 100 % en pratique).

### Forces & Faiblesses
- **Points forts** :
  - Universel : compris par tous les langages, navigateurs et serveurs du monde.
  - Mise en cache ultra-performante au niveau de l'infrastructure web (Cloudflare, Varnish).
  - Découplage complet entre client et serveur.
- **Points faibles** :
  - **Over-fetching** : le serveur renvoie 40 champs alors que l'écran mobile n'en affiche que 2.
  - **Under-fetching / Waterfall** : pour afficher un profil et ses commandes, le client doit enchaîner plusieurs requêtes successives (`/users/1`, puis `/users/1/orders`, puis `/orders/99/items`).
- **Cas d'usage idéaux** : APIs publiques ouvertes, CRUD classiques, intégrations web standards.

## 2. SOAP (Simple Object Access Protocol)

Créé par Microsoft dans les années 1990 et standardisé par le W3C, **SOAP** est un protocole strict et normé basé sur le format XML.

```txt
┌────────────────────────────────────────────────────────┐
│ ENVELOPPE SOAP (XML)                                   │
│  ┌──────────────────────────────────────────────────┐  │
│  │ HEADER (Sécurité WS-Security, Tokens SAML)        │  │
│  └──────────────────────────────────────────────────┘  │
│  ┌──────────────────────────────────────────────────┐  │
│  │ BODY (Opération RPC: <GetUser><Id>42</Id></...>) │  │
│  └──────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

### Fonctionnement & Principes Clés
- **Contrat strict WSDL (Web Services Description Language)** : Un fichier XML formel décrit exhaustivement toutes les méthodes, types de paramètres et exceptions disponibles. Les clients peuvent générer leur code automatiquement à partir du fichier WSDL.
- **Enveloppe XML standardisée** : Chaque message comporte un `<soap:Envelope>`, un `<soap:Header>` (pour la sécurité, les transactions) et un `<soap:Body>` (la charge utile).
- **Indépendance de transport** : SOAP peut transiter via HTTP, mais aussi via SMTP, TCP ou JMS.
- **Standards d'entreprise avancés (WS-*)** :
  - *WS-Security* : chiffrement et signature au niveau du message XML lui-même (indépendamment de HTTPS).
  - *WS-ReliableMessaging* : garantie de remise de message de bout en bout.
  - *WS-AtomicTransaction* : transactions distribuées ACID multi-systèmes.

### Forces & Faiblesses
- **Points forts** :
  - Sécurité et conformité strictes pour les environnements réglementés.
  - Typage fort et validation automatique des messages par rapport au contrat WSDL.
- **Points faibles** :
  - Verbosité extrême : le surcoût de parsing et de bande passante du XML est colossal comparé au JSON ou Protobuf.
  - Rigidité : modifier le contrat WSDL demande une coordination lourde.
- **Cas d'usage idéaux** : Systèmes bancaires historiques, flux interbancaires (SWIFT), télécommunications, passerelles gouvernementales.

## 3. gRPC (Google Remote Procedure Call)

Développé par Google en 2015 et placé sous l'égide de la CNCF, **gRPC** est un framework RPC (*Remote Procedure Call*) à très haute performance, conçu pour les communications internes à faible latence.

```txt
[Service Commandes] ──── Appel binaire Protobuf ────► [Service Paiement]
                    ◄─── (HTTP/2 Multiplexé) ───────
```

### Fonctionnement & Principes Clés
- **Protocol Buffers (Protobuf)** : Au lieu de textes lisibles (JSON ou XML), gRPC utilise une sérialisation binaire ultra-compacte. Les structures de données et les services sont définis dans un fichier `.proto` :
  ```protobuf
  syntax = "proto3";

  service UserService {
    rpc GetUser (UserRequest) returns (UserResponse);
  }

  message UserRequest {
    int32 id = 1;
  }

  message UserResponse {
    int32 id = 1;
    string name = 2;
    string email = 3;
  }
  ```
- **HTTP/2 sous le capot** :
  - **Multiplexage** : des dizaines d'appels simultanés passent dans une seule et unique connexion TCP persistante sans blocage de tête de ligne (*Head-of-Line Blocking*).
  - **Compression des headers HPACK**.
- **4 Modes de communication** :
  1. *Unaire* : Requête simple $\rightarrow$ Réponse simple.
  2. *Server Streaming* : Le client envoie une requête, le serveur répond avec un flux continu de messages.
  3. *Client Streaming* : Le client envoie un flux continu de données, le serveur répond une fois terminé (ex: upload de fichier).
  4. *Bidirectional Streaming* : Flux ouverts et simultanés dans les deux sens.

### Forces & Faiblesses
- **Points forts** :
  - Vitesse foudroyante : jusqu'à 7 à 10 fois plus rapide et 3 fois plus compact que REST/JSON.
  - Génération de code polyglotte automatique (Go, Java, Node.js, Python, C++, Rust).
  - Streaming natif.
- **Points faibles** :
  - Non lisible par un être humain (binaire).
  - Support difficile dans les navigateurs web (nécessite un proxy comme Envoy avec `grpc-web`).
- **Cas d'usage idéaux** : Communication inter-microservices dans un cluster Kubernetes, architectures distribuées haute performance, traitement de flux télémétriques.

## 4. WebSocket

Standardisé par l'IETF (RFC 6455) en 2011, le protocole **WebSocket** permet d'établir une connexion persistante, bidirectionnelle et full-duplex sur une unique socket TCP.

```txt
Client                                            Serveur
  │                                                  │
  │─── HTTP GET /chat (Upgrade: websocket) ─────────►│  (1. Handshake HTTP)
  │◄── 101 Switching Protocols ──────────────────────│
  │                                                  │
  │══════════════════════════════════════════════════│  (2. Connexion TCP ouverte)
  │─── Frame Texte: "Hello!" ───────────────────────►│  (Full-duplex sans overhead)
  │◄── Frame Binaire: [Données temps réel] ──────────│
```

### Fonctionnement & Principes Clés
- **Handshake HTTP Initial** : Le client démarre avec une requête HTTP standard contenant l'en-tête `Upgrade: websocket`. Si le serveur l'accepte, il répond avec le code HTTP `101 Switching Protocols`.
- **Canal TCP Persistant** : Dès lors, le protocole bascule de HTTP à WebSocket (`ws://` ou `wss://` chiffré via TLS). La connexion reste ouverte indéfiniment.
- **Trames ultra-légères (*Frames*)** : Contrairement à HTTP où chaque requête répète des centaines d'octets d'en-têtes (cookies, user-agent), les trames WebSocket n'ont qu'un surcoût d'en-tête de **2 à 10 octets** seulement !
- **Full-Duplex** : Le client et le serveur peuvent s'envoyer des données de façon totalement asynchrone et simultanée.

### Forces & Faiblesses
- **Points forts** :
  - Latence minimale absolue (quelques millisecondes).
  - Le serveur peut « pousser » (*push*) des informations vers le client sans que celui-ci n'ait besoin de faire de requêtes répétées (*polling*).
- **Points faibles** :
  - Maintien d'état côté serveur : chaque connexion consomme de la mémoire (difficile de monter à des millions de sockets ouvertes sans infrastructure dédiée comme Redis Pub/Sub ou Socket.io clusters).
  - Aucun mécanisme de cache HTTP natif.
- **Cas d'usage idéaux** : Messageries instantanées (chats), cours de bourse et cryptos en direct, jeux vidéo multijoueurs par navigateur, tableaux de bord de monitoring live.

## 5. Webhooks (L'API Inversée / Reverse API)

Contrairement aux APIs traditionnelles où le client demande une information au serveur (*Pull*), un **Webhook** permet à un système externe de notifier votre serveur dès qu'un événement survient (*Push*).

```txt
┌──────────────┐     Événement Stripe:      ┌───────────────────────┐
│ Fournisseur  │     "payment_intent.succeeded" │ Votre Serveur Backend │
│ (ex: Stripe) │ ──────────────────────────►│ (POST /webhooks/stripe)│
└──────────────┘   Payload JSON + Signature  └───────────────────────┘
```

### Fonctionnement & Principes Clés
- **Callback HTTP asynchrone** : Vous enregistrez l'URL de votre serveur auprès du service tiers (ex: `https://monsite.com/api/webhooks/stripe`).
- **Déclenchement par Événement** : Lorsqu'un événement survient (ex: prélèvement bancaire réussi, push Git sur GitHub), le service tiers envoie immédiatement une requête `POST` HTTP contenant la charge utile (*payload*) JSON.
- **Sécurisation par Signature Cryptographique** :
  Pour vérifier que la requête provient bien de Stripe ou GitHub et n'est pas une attaque malveillante forgée par un hacker, le fournisseur signe le corps de la requête avec une clé secrète partagée (*Webhook Secret*) et insère la signature dans un header HTTP (ex: `Stripe-Signature` ou `X-Hub-Signature-256`).
- **Idempotence & Retries** :
  Si votre serveur renvoie une erreur 500 ou met plus de 5 secondes à répondre, le fournisseur rejoue la requête selon un calendrier exponentiel (*exponential backoff*). Votre code doit donc être **idempotent** (ne pas créditer deux fois un compte si le même webhook arrive en double).

```typescript
// Exemple de validation de webhook sécurisé (Node.js / Express)
import crypto from "node:crypto";
import { Request, Response } from "express";

export function verifyGithubWebhook(req: Request, res: Response) {
  const signature = req.headers["x-hub-signature-256"] as string;
  const secret = process.env.GITHUB_WEBHOOK_SECRET!;

  // Calcul du HMAC SHA-256 sur le corps brut de la requête
  const hmac = crypto.createHmac("sha256", secret);
  const digest = "sha256=" + hmac.update(JSON.stringify(req.body)).digest("hex");

  // Comparaison à temps constant pour éviter les attaques temporelles (Timing Attacks)
  const isTrusted = crypto.timingSafeEqual(
    Buffer.from(signature || ""),
    Buffer.from(digest)
  );

  if (!isTrusted) {
    return res.status(401).send("Signature invalide !");
  }

  // Traitement de l'événement...
  return res.status(200).send("Événement reçu");
}
```

### Forces & Faiblesses
- **Points forts** :
  - Évite le polling continu (interroger une API toutes les 2 secondes pour savoir si un paiement est validé est une catastrophe en termes de bande passante et de quotas).
  - Réactivité immédiate.
- **Points faibles** :
  - Nécessite que votre serveur expose une URL publique sécurisée (en local, requiert des tunnels comme Ngrok ou Cloudflare Tunnel).
  - Gestion obligatoire de la concurrence, des files d'attente et des doublons.
- **Cas d'usage idéaux** : Notifications de paiement (Stripe, PayPal), pipelines CI/CD (GitHub, GitLab), synchronisation CRM.

## 6. GraphQL

Créé par Facebook en 2012 et rendu open-source en 2015, **GraphQL** est à la fois un langage de requête de données pour les APIs et un moteur d'exécution côté serveur.

```txt
Requête Client:
POST /graphql
{
  user(id: "42") {
    name
    orders(limit: 2) {
      total
      status
    }
  }
}

Réponse Serveur (Exactement ce qui a été demandé):
{
  "data": {
    "user": {
      "name": "Bamba",
      "orders": [
        { "total": 120.50, "status": "DELIVERED" }
      ]
    }
  }
}
```

### Fonctionnement & Principes Clés
- **Endpoint Unique** : Contrairement à REST qui multiplie les routes (`/users`, `/posts`, `/comments`), GraphQL n'utilise généralement qu'une seule route : `POST /graphql`.
- **Piloté par le Client (*Client-Driven*)** : C'est le client frontend qui spécifie rigoureusement les champs dont il a besoin. Le serveur ne renvoie ni plus, ni moins.
  - Résout définitivement l'**Over-fetching** (réception de données superflues).
  - Résout l'**Under-fetching** : récupération en un seul aller-retour de données relationnelles complexes (l'utilisateur, ses factures et ses avis).
- **Schéma et Typage Stricte (SDL)** : Tout est décrit dans un schéma fort (`type Query`, `type Mutation`, `type Subscription`).
- **Arborescence de Résolveurs (*Resolver Tree*)** : Côté serveur, chaque champ du schéma est associé à une fonction résolveur chargée de récupérer la donnée (en BDD, dans un cache ou via une autre API).

### Forces & Faiblesses
- **Points forts** :
  - Expérience développeur frontend exceptionnelle et auto-documentation via l'introspection.
  - Typage de bout en bout automatique avec des générateurs de code (GraphQL Code Generator).
- **Points faibles** :
  - Complexité de mise en cache HTTP : comme toutes les requêtes sont envoyées en `POST` vers la même URL `/graphql`, le cache navigateur classique ne fonctionne pas directement (nécessite des caches applicatifs comme Apollo Client ou Urql).
  - Risque d'attaques par requêtes trop profondes : un client malveillant peut exécuter une requête imbriquée récursive qui met le serveur à genoux.
  - Problème du $N+1$ en base de données sans l'utilisation d'outils comme **DataLoader**.
- **Cas d'usage idéaux** : Applications web et mobiles riches aux interfaces complexes, agrégation de multiples microservices sous une façade unifiée (*Backend-For-Frontend* / BFF).

## 7. WebRTC (Web Real-Time Communication)

Standardisé conjointement par le W3C et l'IETF, **WebRTC** permet d'établir une communication directe **pair-à-pair (*Peer-to-Peer*)** en temps réel entre deux navigateurs ou périphériques pour échanger de la vidéo, de l'audio et des données brutes avec une latence sub-seconde (< 200 ms).

```txt
┌──────────────┐         Serveur de Signalisation          ┌──────────────┐
│  Navigateur  │ ◄─────── (Échange SDP & Candidats) ──────►│  Navigateur  │
│   Client A   │                                           │   Client B   │
└──────┬───────┘                                           └──────┬───────┘
       │                                                          │
       └═════════════════ Flux Média P2P Direct ══════════════════┘
                         (UDP / SRTP - Zéro Serveur Intermédiaire)
```

### Fonctionnement & Principes Clés
- **Communication Pair-à-Pair (P2P)** : Une fois la liaison négociée, les flux audio/vidéo ne transitent plus par votre serveur web : ils passent directement d'un utilisateur à l'autre via le protocole UDP sécurisé (SRTP).
- **Le Processus de Signalisation (*Signaling*)** :
  Avant que deux machines puissent se parler en direct, elles doivent échanger leurs coordonnées réseau et leurs capacités médias. Cette négociation initiale passe par un serveur de signalisation (souvent en WebSocket) via le protocole **SDP** (*Session Description Protocol*) avec un échange d'*Offer* et d'*Answer*.
- **Le Traversée des Pare-feux (NAT Traversal via STUN / TURN / ICE)** :
  Dans le monde réel, les utilisateurs sont cachés derrière des box Internet, des routeurs et des pare-feux d'entreprise avec des adresses IP privées.
  - **STUN** (*Session Traversal Utilities for NAT*) : Permet à un client de découvrir son adresse IP publique réelle et son port ouvert sur Internet.
  - **TURN** (*Traversal Using Relays around NAT*) : Serveur de relais utilisé en dernier recours si le pare-feu bloque complètement la connexion directe P2P (environ 15 % des appels mondiaux).
  - **ICE** (*Interactive Connectivity Establishment*) : L'algorithme qui teste l'ensemble des chemins possibles et sélectionne le plus rapide.
- **Data Channels** : Au-delà de l'audio et de la vidéo, WebRTC propose `RTCDataChannel` permettant de transférer des paquets de données arbitraires en P2P à très haute cadence.

### Forces & Faiblesses
- **Points forts** :
  - Latence ultra-faible inégalable (< 200 millisecondes, indispensable pour la voix humaine).
  - Économie colossale de bande passante serveur : votre infrastructure n'achemine pas les téraoctets de flux vidéo.
  - Chiffrement de bout en bout obligatoire (DTLS et SRTP).
- **Points faibles** :
  - Complexité de mise en place (gestion des serveurs STUN/TURN et de la signalisation).
  - Ne scale pas bien au-delà de 4 à 6 personnes en P2P pur (*Full Mesh*) : la bande passante montante de chaque participant sature. Pour des réunions à 50 personnes (Zoom, Google Meet), il faut introduire un serveur intermédiaire de type **SFU** (*Selective Forwarding Unit*).
- **Cas d'usage idéaux** : Visioconférence (Google Meet, Discord), streaming interactif de cloud gaming, partage de fichiers volumineux en direct entre navigateurs.

## 🧭 Comment Choisir la Bonne API ? (Guide de Décision Rapide)

```txt
Avez-vous besoin de communiquer en temps réel ?
 ├── OUI : S'agit-il de vidéo ou d'audio interactif entre humains ?
 │     ├── OUI ──────────────────────────────────────────────► WebRTC
 │     └── NON : Données légères poussées fréquemment ? ─────► WebSocket
 │
 └── NON : Avez-vous besoin qu'un tiers vous notifie d'un fait ?
       ├── OUI ──────────────────────────────────────────────► Webhook
       └── NON : Échange classique entre client et serveur ?
             ├── S'agit-il de microservices internes critiques en vitesse ? ──► gRPC
             ├── Les clients ont-ils des besoins d'affichage très variés ? ──► GraphQL
             ├── Système patrimonial bancaire avec contrat formel ? ─────────► SOAP
             └── Cas standard par défaut pour 80% des besoins web ? ────────► REST
```
