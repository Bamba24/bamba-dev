# Authentification Token vs Session : Le Comparatif Ultime avec Exemples de Code

Dans le monde du développement web, chaque requête HTTP est par essence **sans état (*stateless*)**. Une fois la réponse envoyée, le serveur oublie complètement qui vous êtes.

Pour maintenir une continuité d'identité lorsqu'un utilisateur navigue de page en page ou déclenche une action sur une API, deux grandes philosophies s'affrontent depuis des années :
1. **L'authentification par Session (Stateful)**
2. **L'authentification par Token (Stateless - ex: JWT)**

Quel modèle choisir pour votre prochaine application ? Pourquoi les banques ne jurent-elles que par les sessions tandis que les géants du cloud ne jurent que par les tokens ? Et comment allier le meilleur des deux mondes en production ?

Voici le comparatif complet, décortiqué au niveau architectural et illustré d'exemples de code concrets.

---

## 1. Le Match Architectural : Stateful vs Stateless

```txt
┌────────────────────────────────────────────────────────────────────────┐
│                   SESSION vs TOKEN : LE MATCH                          │
├──────────────────────────┬─────────────────────────────────────────────┤
│ AUTHENTIFICATION SESSION │ AUTHENTIFICATION TOKEN (JWT)                │
│ (Stateful - En Mémoire)  │ (Stateless - Cryptographique)               │
├──────────────────────────┼─────────────────────────────────────────────┤
│ 1. Client envoie login   │ 1. Client envoie login                      │
│ 2. Serveur crée session  │ 2. Serveur signe un JWT (Header.Payload.Sig)│
│    en base/Redis         │    sans rien stocker en base                │
│ 3. Renvoie un Session_ID │ 3. Renvoie le token au client               │
│    en Cookie HttpOnly    │                                             │
│ 4. Client envoie Cookie  │ 4. Client envoie: Authorization: Bearer <T> │
│ 5. Serveur cherche l'ID  │ 5. Serveur vérifie la signature mathématique│
│    en base (Look-up DB)  │    avec sa clé secrète (Zéro BDD requise)   │
└──────────────────────────┴─────────────────────────────────────────────┘
```

---

### 1.1 L'Authentification par Session (Stateful)

Dans une architecture par session, **le serveur garde la mémoire absolue de qui est connecté**.

#### Le Cycle de Vie d'une Session :
1. L'utilisateur envoie ses identifiants (`POST /login`).
2. Le serveur vérifie le mot de passe haché en base de données.
3. Le serveur génère un identifiant de session unique et aléatoire (ex: un UUID cryptographique `sess_98a7f1...`).
4. Le serveur stocke cet identifiant et les données associées (ID utilisateur, rôle, date de création) dans un magasin d'état : généralement **Redis** ou une table SQL `sessions`.
5. Le serveur retourne cet identifiant dans un en-tête HTTP :
   `Set-Cookie: session_id=sess_98a7f1...; HttpOnly; Secure; SameSite=Lax`
6. À chaque requête suivante, le navigateur renvoie automatiquement ce cookie.
7. Le serveur interroge son magasin de sessions (Redis) pour vérifier si l'identifiant existe et charger les informations de l'utilisateur.

---

### 1.2 L'Authentification par Token (Stateless - JWT)

Dans une architecture par token, **le serveur ne stocke rien**. C'est le client qui transporte son identité avec lui.

#### L'Anatomie d'un JWT (JSON Web Token) :
Un JWT est composé de trois parties encodées en Base64Url et séparées par des points (`xxxxx.yyyyy.zzzzz`) :
1. **Header** : Spécifie l'algorithme de hachage (ex: `HS256` ou `RS256`).
2. **Payload (Claims)** : Contient les données utilisateur (`userId`, `role`, date d'expiration `exp`).
3. **Signature** : L'empreinte cryptographique calculée à partir du Header, du Payload et d'une clé secrète connue uniquement du serveur.

```txt
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│    HEADER    │  .  │   PAYLOAD    │  .  │  SIGNATURE   │
│  {"alg":     │     │  {"sub":     │     │  HMACSHA256( │
│   "HS256"}   │     │   "usr_123"} │     │   base64,    │
│              │     │              │     │   secret)    │
└──────────────┘     └──────────────┘     └──────────────┘
```

#### Le Cycle de Vie d'un Token :
1. L'utilisateur s'authentifie (`POST /login`).
2. Le serveur valide les identifiants et génère le JWT signé cryptographiquement.
3. Le serveur retourne le token dans le corps de réponse JSON.
4. Le client conserve le token et l'ajoute dans l'en-tête de chaque requête API :
   `Authorization: Bearer eyJhbGciOiJIUzI1...`
5. Le serveur vérifie mathématiquement la signature du token à l'aide de sa clé secrète. **Aucun appel à la base de données n'est requis** pour vérifier la validité de l'identité.

## 2. Tableau Comparatif Détaillé

| Critère | Session (Stateful) | Token / JWT (Stateless) |
| :--- | :--- | :--- |
| **Stockage Serveur** | **Obligatoire** : cluster Redis ou table SQL. | **Aucun** : le serveur ne retient rien en mémoire. |
| **Stockage Client** | Cookie `HttpOnly` sécurisé. | Cookie `HttpOnly` ou mémoire d'application. |
| **Scalabilité Horizontale** | Nécessite un cluster Redis partagé ou des sticky sessions. | **Native et immédiate** : n'importe quel conteneur valide le token instantanément. |
| **Révocation / Déconnexion** | **Immédiate et absolue** : il suffit d'effacer la clé dans Redis. | **Complexe** : le token reste valide jusqu'à son expiration `exp`. |
| **Taille des Données Réseau** | **Minime** : un simple ID opaque d'une trentaine d'octets. | **Plus lourd** : données claims + signature (500 à 1500 octets). |
| **Vulnérabilité Principale** | Attaques **CSRF** (si le cookie SameSite est mal configuré). | Attaques **XSS** (si le token est stocké dans le `localStorage`). |
| **Cas d'Usage Idéal** | Monolithes web, intranets, plateformes bancaires. | Microservices distribués, APIs publiques, applications mobiles. |

## 3. Implémentation 1 : Authentification par Session avec Express & Redis

Dans cet exemple TypeScript, nous configurons un serveur Express utilisant `express-session` avec Redis en magasin de persistance.

```typescript
import express, { Request, Response, NextFunction } from "express";
import session from "express-session";
import { createClient } from "redis";
import { RedisStore } from "connect-redis";

const app = express();
app.use(express.json());

// 1. Initialisation de la connexion Redis
const redisClient = createClient({ url: "redis://localhost:6379" });
redisClient.connect().catch(console.error);

// 2. Configuration du middleware de session sécurisé
app.use(
  session({
    store: new RedisStore({ client: redisClient, prefix: "sess:" }),
    secret: "votre_cle_secrete_ultra_securisee_de_production",
    resave: false,
    saveUninitialized: false,
    name: "__Secure-sid",
    cookie: {
      httpOnly: true, // Empêche tout script JavaScript côté client de lire le cookie (anti-XSS)
      secure: process.env.NODE_ENV === "production", // Transmis uniquement sur connexion HTTPS
      sameSite: "lax", // Empêche l'envoi du cookie lors de requêtes inter-sites frauduleuses (anti-CSRF)
      maxAge: 1000 * 60 * 60 * 24, // 24 heures de validité
    },
  })
);

// Typage TypeScript des données stockées en session
declare module "express-session" {
  interface SessionData {
    userId?: string;
    role?: string;
  }
}

// 3. Route de Connexion (Login)
app.post("/api/auth/login", (req: Request, res: Response) => {
  const { email, password } = req.body;

  // Simulation de vérification en base de données
  if (email === "admin@bambadev.com" && password === "secret123") {
    // Écriture de l'état dans la session (automatiquement persisté dans Redis)
    req.session.userId = "usr_007";
    req.session.role = "ADMIN";

    return res.status(200).json({ message: "Connexion réussie par session" });
  }

  return res.status(401).json({ error: "Identifiants invalides" });
});

// 4. Middleware de vérification de session active
function requireAuth(req: Request, res: Response, next: NextFunction) {
  if (!req.session.userId) {
    return res.status(401).json({ error: "Non autorisé : session invalide ou expirée" });
  }
  next();
}

// 5. Route protégée
app.get("/api/dashboard", requireAuth, (req: Request, res: Response) => {
  return res.json({
    message: "Accès autorisé aux données de gestion",
    userId: req.session.userId,
    role: req.session.role,
  });
});

// 6. Révocation Instantanée (Logout)
app.post("/api/auth/logout", (req: Request, res: Response) => {
  req.session.destroy((err) => {
    if (err) return res.status(500).json({ error: "Erreur de déconnexion" });
    res.clearCookie("__Secure-sid");
    return res.json({ message: "Session révoquée avec succès côté serveur" });
  });
});
```

## 4. Implémentation 2 : Authentification par Token JWT (Stateless)

Dans cette approche, le serveur génère un jeton cryptographique auto-suffisant. La vérification de validité se fait uniquement par calcul mathématique de la signature, sans jamais interroger la base de données.

```typescript
import express, { Request, Response, NextFunction } from "express";
import jwt from "jsonwebtoken";

const app = express();
app.use(express.json());

const JWT_SECRET = "phrase_secrete_cryptographique_inviolable";

interface UserPayload {
  userId: string;
  email: string;
  role: string;
}

interface AuthenticatedRequest extends Request {
  user?: UserPayload;
}

// 1. Route de Connexion (Login) : Création et Signature du Token
app.post("/api/auth/login", (req: Request, res: Response) => {
  const { email, password } = req.body;

  if (email === "user@bambadev.com" && password === "secret123") {
    const payload: UserPayload = {
      userId: "usr_9981",
      email: "user@bambadev.com",
      role: "DEVELOPER",
    };

    // Signature avec expiration courte (15 minutes)
    const token = jwt.sign(payload, JWT_SECRET, {
      expiresIn: "15m",
      algorithm: "HS256",
    });

    return res.json({
      accessToken: token,
      tokenType: "Bearer",
      expiresIn: 900,
    });
  }

  return res.status(401).json({ error: "Identifiants invalides" });
});

// 2. Middleware de Vérification de Token (Stateless)
function verifyJwt(
  req: AuthenticatedRequest,
  res: Response,
  next: NextFunction
) {
  const authHeader = req.headers.authorization;

  if (!authHeader || !authHeader.startsWith("Bearer ")) {
    return res.status(401).json({ error: "Format d'autorisation invalide (Bearer requis)" });
  }

  const token = authHeader.split(" ")[1];

  try {
    // Vérification mathématique SANS AUCUNE REQUÊTE BASE DE DONNÉES
    const decoded = jwt.verify(token, JWT_SECRET) as UserPayload;
    req.user = decoded;
    next();
  } catch (error) {
    if (error instanceof jwt.TokenExpiredError) {
      return res.status(401).json({ error: "Le jeton a expiré" });
    }
    return res.status(403).json({ error: "Signature de jeton invalide" });
  }
}

// 3. Route protégée
app.get(
  "/api/profile",
  verifyJwt,
  (req: AuthenticatedRequest, res: Response) => {
    return res.json({
      message: `Profil chargé pour ${req.user?.email}`,
      user: req.user,
    });
  }
);
```

## 5. Le Vainqueur en Production : La Stratégie Hybride à Double Jeton

Pourquoi choisir entre la vitesse du Token et le contrôle absolu de la Session quand on peut avoir les deux ?

En production moderne, la méthode recommandée consiste à combiner un **Access Token court** et un **Refresh Token sécurisé** :

```txt
┌────────────────────────────────────────────────────────────────────────┐
│                        LE PATTERN DOUBLE TOKEN                         │
├────────────────────────────────────────────────────────────────────────┤
│ 1. Access Token (JWT) :                                                │
│    • Durée de vie très courte (10 à 15 minutes).                       │
│    • Utilisé dans les en-têtes Authorization: Bearer.                  │
│    • Permet des appels ultrarapides aux microservices sans DB.         │
├────────────────────────────────────────────────────────────────────────┤
│ 2. Refresh Token :                                                     │
│    • Durée de vie plus longue (7 à 30 jours).                          │
│    • Stocké impérativement dans un Cookie HttpOnly, Secure, SameSite.  │
│    • Enregistré en base de données avec rotation systématique.         │
│    • Permet la révocation immédiate (bannissement, changement de mdp). │
└────────────────────────────────────────────────────────────────────────┘
```

1. **Au login** : l'utilisateur reçoit son `accessToken` (15 min) et un cookie contenant le `refreshToken` (14 jours).
2. **Durant la navigation** : le client utilise l'`accessToken` pour consommer les APIs à haute vitesse.
3. **À l'expiration de l'`accessToken`** : le frontend appelle silencieusement le endpoint `/api/auth/refresh`. Le serveur vérifie la validité du `refreshToken` en base et émet une nouvelle paire de tokens.
4. **En cas de déconnexion ou de compromission** : le serveur supprime le `refreshToken` de la base de données. L'utilisateur est expulsé au bout de quelques minutes maximum.

## 6. Synthèse : Quand Choisir Quoi ?

- **Choisissez la Session (Stateful avec Redis)** si :
  - Votre application est un monolithe classique ou un dashboard d'entreprise (Next.js, Laravel, Django).
  - La sécurité financière exige la possibilité d'expulser un utilisateur à la seconde près.
  - Vous souhaitez vous prémunir nativement contre les failles XSS en utilisant des cookies `HttpOnly`.
- **Choisissez le Token (Stateless / JWT)** si :
  - Vous développez des APIs publiques consommées par des applications mobiles iOS / Android.
  - Votre architecture est éclatée en microservices et vous ne voulez pas saturer une base Redis centrale.
  - Vous mettez en place le SSO (*Single Sign-On*) entre plusieurs domaines distincts.
