# Loi de Déméter, Fail Fast, SoC et Boy Scout Rule : L'Art du Code Robuste et Propre

Écrire du code qui « marche » le jour de la démonstration est à la portée de n'importe quel débutant. Mais concevoir un système qui continue de fonctionner 3 ans plus tard sans devenir un cauchemar de maintenance exige une véritable discipline d'ingénierie.

Au-delà des grands paradigmes comme SOLID ou DRY, la qualité quotidienne d'un logiciel repose sur quatre règles d'hygiène et d'architecture fondamentales :
1. **La Loi de Déméter (LoD)** : réduire le couplage entre objets.
2. **Le Principe Fail Fast** : intercepter les erreurs dès la porte d'entrée.
3. **La Séparation des Préoccupations (SoC)** : organiser le système en métiers étanches.
4. **La Règle du Scout (Boy Scout Rule)** : améliorer continuellement la base de code.

Voici comment maîtriser ces 4 principes avec des **analogies concrètes** et du **code TypeScript**.

## 1. 🤫 La Loi de Déméter (LoD) — Le Principe de Moindre Connaissance

> **Règle :** Un composant ne doit connaître que ses collaborateurs immédiats et ne jamais naviguer dans les entrailles de ses dépendances.

### L'Analogie du Monde Réel
> **L'Analogie du Marchand de Journaux :** Lorsque vous achetez un magazine chez le buraliste, vous ne lui tendez pas votre portefeuille ouvert en lui disant : *« Tenez, ouvrez mon portefeuille, cherchez la poche à monnaie, prenez 3 euros et refermez-le »*. Vous demandez le montant, vous sortez vous-même les 3 euros, et vous les donnez au commerçant. Le commerçant n'a aucun droit de savoir comment votre portefeuille est structuré.

### En Code TypeScript

#### ❌ Le Code « Accident de Train » (*Train Wreck*)
Une longue chaîne d'accès qui traverse 5 couches internes :

```typescript
// ❌ CATASTROPHE DE COUPLAGE FORT (Train Wreck)
function printEmployeeZipCode(employee: Employee) {
  // Si demain 'department' est renommé ou devient optionnel, ce code explose !
  const zip = employee.getCompany().getDepartment().getManager().getAddress().getZipCode();
  console.log(zip);
}
```
*Pourquoi c'est dangereux :* Cette fonction dépend de la structure interne de `Employee`, de `Company`, de `Department`, de `Manager` et de `Address`. Une modification n'importe où dans cette chaîne brisera le code.

#### ✅ La Solution Conforme à Déméter
Encapsuler la demande au niveau du collaborateur direct :

```typescript
// ✅ L'employé délègue en interne sans exposer ses entrailles
function printEmployeeZipCode(employee: Employee) {
  const zip = employee.getManagerZipCode();
  console.log(zip);
}
```

## 2. ⚡ Le Principe Fail Fast — Échouer Tôt et Brutalement

> **Règle :** Une fonction doit vérifier et valider immédiatement ses paramètres d'entrée. Si une condition n'est pas remplie, arrêtez l'exécution sur-le-champ au lieu de laisser l'erreur se propager.

### L'Analogie du Monde Réel
> **L'Analogie du Videur de Club :** Le videur à l'entrée d'un club vérifie votre pièce d'identité et votre tenue à la porte. Il ne vous laisse pas entrer dans l'établissement pour venir vous expulser 2 heures plus tard au milieu de la piste de danse pendant que vous commandez un verre. Il refuse l'accès dès la porte d'entrée.

### En Code TypeScript

#### ❌ L'Anti-Pattern : La Pyramide de l'Enfer (Indentations Multiples)
Le code s'enfonce dans des niveaux d'indentation vertigineux :

```typescript
// ❌ CODE ENTONNOIR DIFFICILE À LIRE
function processTransfer(account: Account | null, amount: number) {
  if (account !== null) {
    if (account.isActive) {
      if (amount > 0) {
        if (account.balance >= amount) {
          account.balance -= amount;
          return { success: true };
        } else {
          throw new Error("Solde insuffisant");
        }
      } else {
        throw new Error("Montant invalide");
      }
    } else {
      throw new Error("Compte inactif");
    }
  } else {
    throw new Error("Compte inexistant");
  }
}
```

#### ✅ La Solution Fail Fast : Les Clauses de Garde (*Guard Clauses*)
On vérifie et on rejette les cas d'erreur dès les premières lignes pour garder le flux nominal plat et limpide :

```typescript
// ✅ FAIL FAST : SORTIE IMMÉDIATE EN CAS D'ANOMALIE
function processTransfer(account: Account | null, amount: number) {
  if (!account) throw new Error("Compte inexistant");
  if (!account.isActive) throw new Error("Compte inactif");
  if (amount <= 0) throw new Error("Montant invalide");
  if (account.balance < amount) throw new Error("Solde insuffisant");

  // Cas nominal sans indentation :
  account.balance -= amount;
  return { success: true };
}
```

## 3. 🧩 SoC — *Separation of Concerns* (Séparation des Préoccupations)

> **Règle :** Découpez le programme en sections distinctes, où chaque section traite d'un sujet exclusif.

### L'Analogie du Monde Réel
> **L'Analogie de la Brigade de Restaurant :** Dans un grand restaurant, le chef de cuisine prépare les plats, le sommelier sélectionne les vins, le serveur apporte les assiettes en salle, et le caissier encaisse les paiements. Si le chef cuisinier devait quitter ses fourneaux pour courir en salle servir les clients et rendre la monnaie, la nourriture brûlerait et la caisse serait fausse.

### En Code TypeScript (Exemple Web Moderne)

#### ❌ Le Composant « Monolithe Spaghetti »
Un composant React qui fait des requêtes SQL/HTTP en dur, applique des calculs de TVA et gère l'affichage :

```typescript
// ❌ TOUT EST MÉLANGÉ DANS LE COMPOSANT VISUEL
export function BadInvoiceWidget({ invoiceId }: { invoiceId: string }) {
  const [data, setData] = useState<any>(null);

  useEffect(() => {
    // 1. Préoccupation Réseau & Données
    fetch(`/api/invoices/${invoiceId}`)
      .then(res => res.json())
      .then(invoice => {
        // 2. Préoccupation Logique Métier & Calculs
        const vat = invoice.rawAmount * 0.20;
        const total = invoice.rawAmount + vat;
        setData({ ...invoice, total });
      });
  }, [invoiceId]);

  // 3. Préoccupation Affichage UI
  return <div>Facture : {data?.total} €</div>;
}
```

#### ✅ La Solution Conforme à SoC
On sépare distinctement les trois préoccupations :

```typescript
// 1. Calcul Métier Pur (Testable sans React !)
export function computeInvoiceTotal(rawAmount: number): number {
  const VAT_RATE = 0.20;
  return rawAmount * (1 + VAT_RATE);
}

// 2. Hook de Données (Préoccupation réseau isolée)
export function useInvoice(invoiceId: string) {
  return useQuery({
    queryKey: ["invoice", invoiceId],
    queryFn: () => fetchInvoiceById(invoiceId),
    select: (data) => ({
      ...data,
      total: computeInvoiceTotal(data.rawAmount),
    }),
  });
}

// 3. Composant d'Interface Pur (Présentation exclusive)
export function CleanInvoiceWidget({ invoiceId }: { invoiceId: string }) {
  const { data, isLoading } = useInvoice(invoiceId);

  if (isLoading) return <Spinner />;
  return <div>Facture : {data?.total} €</div>;
}
```

## 4. 🏕️ The Boy Scout Rule — La Règle du Scout

> **Règle :** « Laisse le campement toujours plus propre que tu ne l'as trouvé en arrivant. »

### L'Analogie du Monde Réel
> **L'Analogie du Sentier de Randonnée :** Lorsque des scouts campent en forêt, ils ne nettoient pas seulement leurs propres détritus. S'ils aperçoivent une bouteille en plastique ou une vieille canette abandonnée par un précédent promeneur, ils la ramassent et la jettent à la poubelle. Grâce à ce geste minime et répété, la forêt devient plus belle de jour en jour.

### En Pratique dans Votre Codebase
Vous n'avez pas besoin de bloquer deux semaines pour faire un « grand refactoring » que le management refusera toujours. 

À chaque fois que vous ouvrez un fichier pour implémenter une nouvelle fonctionnalité ou corriger un bug :
1. Renommez cette variable obscure `tmp2` en un nom explicite `activeUserSession`.
2. Supprimez ce bloc de 15 lignes de code commenté datant de 2022.
3. Ajoutez le typage TypeScript manquant à une fonction typée en `any`.
4. Extrayez une constante magique (ex: `86400000` $\rightarrow$ `ONE_DAY_IN_MS`).

> **L'effet boule de neige :** Si 5 développeurs appliquent la règle du scout tous les jours sur 2 fichiers, votre codebase subit **2 000 petites améliorations par an**. La dette technique ne s'accumule plus : elle diminue naturellement.

## 📋 Synthèse des 4 Bonnes Pratiques

| Principe | Objectif Majeur | Geste Quotidien du Développeur |
| :--- | :--- | :--- |
| **Loi de Déméter (LoD)** | Découplage strict | Bannir les chaînes d'appels `a.b().c().d()`. Demander au collaborateur direct. |
| **Fail Fast** | Clarté et robustesse | Remplacer les `if` imbriqués par des *Guard Clauses* en haut de fonction. |
| **SoC** | Modularité | Séparer strictement la vue graphique, la plomberie réseau et le calcul métier. |
| **Boy Scout Rule** | Hygiène continue | Nettoyer une petite imperfection sur chaque fichier modifié avant de commiter. |
