# TCP/IP, Sockets et QUIC : Les Fondamentaux Réseau du Développeur

Dans la plupart des formations au développement web, le réseau est abordé comme une boîte noire magique : vous appelez `fetch('https://api.mondomaine.com')`, et une réponse JSON apparaît comme par enchantement.

Mais le jour où votre application Node.js ou Go s'effondre avec une erreur `ECONNRESET`, `ETIMEDOUT`, ou quand votre serveur sature avec des dizaines de milliers de connexions coincées dans l'état `TIME_WAIT`, cette abstraction s'envole en fumée.

Pour franchir le cap de développeur senior, vous devez comprendre ce qui se passe **sous la couche applicative** : comment le noyau Linux alloue des sockets, comment TCP négocie la fiabilité, et pourquoi le web moderne migre massivement vers **QUIC et HTTP/3**.

## 1. Modèle OSI vs Modèle TCP/IP : La Réalité Pratique

Les manuels scolaires enseignent les 7 couches du modèle OSI. Mais sur les serveurs de production, seuls les **4 niveaux du modèle TCP/IP** comptent réellement :

```txt
┌──────────────────────────────────────────────┐
│ 1. Application (HTTP, WebSockets, DNS, SSH)   │ ◄── Votre code applicatif
├──────────────────────────────────────────────┤
│ 2. Transport (TCP, UDP, QUIC)                │ ◄── Géré par le Noyau de l'OS (Kernel)
├──────────────────────────────────────────────┤
│ 3. Internet (IPv4, IPv6, ICMP)               │ ◄── Routage par paquets IP
├──────────────────────────────────────────────┤
│ 4. Accès Réseau (Ethernet, Wi-Fi, Fibre)     │ ◄── Cartes réseau physiques (NIC)
└──────────────────────────────────────────────┘
```

Votre serveur applicatif (Node.js, Rust, Go, Python) ne manipule jamais directement les paquets de la carte réseau. Il interagit avec le noyau via une interface système universelle : **le Socket**.

## 2. Anatomie d'un Socket Réseau

Sur les systèmes UNIX et Linux, **tout est fichier**. Un socket réseau est simplement un **descripteur de fichier** (*File Descriptor* ou `fd`) associé à des tampons mémoire (*buffers*) gérés par le noyau.

```txt
Processus Applicatif (User Space)
      │               ▲
 write(fd, data)   read(fd, buffer)
      ▼               │
──────────────────────┼──────────────────────
Noyau Linux (Kernel Space)
 ┌─────────────────┐ ┌─────────────────┐
 │ Send Buffer     │ │ Receive Buffer  │
 │ (SO_SNDBUF)     │ │ (SO_RCVBUF)     │
 └────────┬────────┘ └────────▲────────┘
          │                   │
          ▼ (Segmentation)    │ (Réassemblage)
   [ Carte Réseau / Pilote NIC ]
```

### Le cycle de vie d'un socket serveur :
1. **`socket()` :** Demande au noyau la création d'un descripteur de communication.
2. **`bind(ip, port)` :** Lie le socket à une adresse IP et un port spécifique (ex: `0.0.0.0:3000`).
3. **`listen(backlog)` :** Indique au noyau de commencer à accepter les connexions entrantes et définit la taille de la file d'attente (*backlog*).
4. **`accept()` :** Extrait une connexion établie de la file d'attente et crée un *nouveau* socket dédié à ce client particulier, laissant le socket principal continuer d'écouter.

## 3. TCP : La Fiabilité au Prix de la Latence

TCP (Transmission Control Protocol) est un protocole **orienté connexion**. Il garantit que chaque octet envoyé arrive à destination, sans corruption et dans l'ordre exact.

### A. Le 3-Way Handshake (Établissement)
Avant d'envoyer le moindre octet de données HTTP, TCP doit établir un dialogue :

```txt
Client                                    Serveur
  │                                          │
  │ ─── 1. SYN (seq = 100) ────────────────> │  « Je veux me connecter »
  │                                          │
  │ <── 2. SYN-ACK (seq = 300, ack = 101) ── │  « Reçu, je suis d'accord »
  │                                          │
  │ ─── 3. ACK (ack = 301) ────────────────> │  « Parfait, connexion ouverte »
  │                                          │
  ▼ [ CONNEXION ÉTABLIE - Échange de données HTTP ]
```

Ce handshake impose **un aller-retour complet (1 RTT)** de latence avant même d'entamer le handshake cryptographique TLS.

### B. La Fermeture et le Mystère du `TIME_WAIT`
La fermeture d'une connexion TCP s'effectue en 4 étapes (`FIN`, `ACK`, `FIN`, `ACK`). 

Le côté qui initie la fermeture passe alors dans l'état **`TIME_WAIT`** pendant généralement 60 à 120 secondes :
- **Pourquoi cet état existe-t-il ?** Pour s'assurer que les éventuels paquets TCP retardés sur Internet ne viennent pas polluer une nouvelle connexion qui réutiliserait le même quadruplet `(IP source, Port source, IP dest, Port dest)`.
- **Le piège en prod :** Si votre microservice ouvre et ferme en boucle des connexions HTTP/1.1 sans réutiliser les connexions (*Keep-Alive*), vous épuiserez la totalité des 65 535 ports éphémères du système (`EADDRNOTAVAIL`).

## 4. Contrôle de Congestion : Pourquoi TCP Ralentit

Internet est un réseau à commutation de paquets non garanti. Si un serveur expédie des données plus vite que les routeurs intermédiaires ne peuvent les acheminer, les tampons saturent et des paquets sont abandonnés (*packet drop*).

TCP intègre des algorithmes de contrôle de flux et de congestion :
- **Slow Start :** La connexion démarre avec une fenêtre de congestion réduite (`cwnd`), puis double la quantité de paquets envoyés à chaque acquittement réussi.
- **CUBIC vs BBR :** Traditionnellement, TCP CUBIC interprète la perte de paquets comme un signal de congestion et divise immédiatement son débit par deux. Le nouvel algorithme **BBR** (développé par Google) mesure le débit goulot réel et la latence minimale (RTT), maintenant un débit maximal même sur les réseaux avec un léger taux de perte.

## 5. UDP : Vitesse Pure et Simplicité Radicale

À l'opposé de TCP, **UDP (User Datagram Protocol)** est un protocole sans connexion (*connectionless*) :
- Zéro handshake préalable.
- Zéro acquittement (ACK) ni retransmission automatique.
- Zéro garantie de livraison ou d'ordre des paquets.
- Un en-tête ultra-léger de seulement **8 octets** (contre 20 à 60 octets pour TCP).

```txt
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ Port Source  │ Port Dest.   │ Longueur UDP │ Checksum     │
│ (16 bits)    │ (16 bits)    │ (16 bits)    │ (16 bits)    │
└──────────────┴──────────────┴──────────────┴──────────────┘
```

> [!NOTE]
> UDP est idéal lorsque la fraîcheur de la donnée compte plus que son exhaustivité : jeux vidéo multijoueurs (la position du joueur d'il y a 200 ms est inutile), streaming vidéo en direct (WebRTC), et requêtes DNS rapides.

## 6. La Révolution QUIC et HTTP/3

Depuis 30 ans, le web reposait sur TCP. Pourtant, TCP souffre d'un défaut structurel majeur : **le blocage en tête de ligne (Head-of-Line Blocking)**.

### Le Problème du Head-of-Line Blocking sur HTTP/2
Avec HTTP/2, plusieurs requêtes sont multiplexées sur une unique connexion TCP. Si un seul paquet d'un flux CSS est perdu sur le réseau, le noyau bloque *tous* les flux (JavaScript, images, requêtes API) jusqu'à ce que le paquet manquant soit réexpédié, car TCP exige une livraison séquentielle stricte.

### La Solution QUIC (HTTP/3)
QUIC résout ce problème en s'exécutant **par-dessus UDP** dans l'espace utilisateur :

```txt
┌──────────────────────────────────────────────┐
│                 HTTP/3                       │
├──────────────────────────────────────────────┤
│  QUIC (Chiffrement TLS 1.3 + Flux Indépendants) │
├──────────────────────────────────────────────┤
│                  UDP                         │
├──────────────────────────────────────────────┤
│                   IP                         │
└──────────────────────────────────────────────┘
```

### Avantages majeurs de QUIC :
1. **Zéro Head-of-Line Blocking :** Chaque flux logique au sein de la connexion est totalement indépendant. La perte d'un paquet sur une image ne ralentit pas l'exécution de l'API critique.
2. **Établissement de Connexion 0-RTT / 1-RTT :** QUIC fusionne le handshake de transport et le chiffrement TLS 1.3 en un seul échange.
3. **Migration de Connexion :** Si un utilisateur passe de la 4G au Wi-Fi, son adresse IP change. Avec TCP, la connexion est rompue. Avec QUIC, un identifiant de connexion (*Connection ID*) unique permet à la session de survivre sans interruption.

## 7. Gestion de la Backpressure au Niveau Socket

En tant que développeur, comprendre les sockets permet d'éviter l'épuisement mémoire lorsque le client lit plus lentement que le serveur ne produit. C'est le principe de la **Backpressure**.

Exemple d'implémentation d'un serveur TCP robuste en TypeScript avec gestion native de backpressure :

```typescript
import * as net from 'node:net';

const server = net.createServer((socket: net.Socket) => {
  // Identification de l'adresse distante du socket
  const remoteAddress = `${socket.remoteAddress}:${socket.remotePort}`;

  // Configuration du socket
  socket.setKeepAlive(true, 30_000); // Détecte les connexions mortes
  socket.setNoDelay(true);          // Désactive l'algorithme de Nagle (envoi immédiat)

  socket.on('data', (chunk: Buffer) => {
    // Si le tampon d'émission du socket est plein, write() retourne false
    const canContinueWriting = socket.write(chunk);

    if (!canContinueWriting) {
      // Le client lit trop lentement : on met en pause la lecture pour soulager la RAM
      socket.pause();
    }
  });

  // Événement déclenché lorsque le noyau a vidé le tampon SO_SNDBUF
  socket.on('drain', () => {
    // On reprend la réception normale
    socket.resume();
  });

  socket.on('error', (err: Error) => {
    // Gestion propre des fermetures inattendues
    socket.destroy();
  });
});

server.listen(8080, () => {
  // Serveur prêt à écouter les sockets entrants
});
```

## Comparatif Synthétique des Protocoles de Transport

| Caractéristique | TCP (Transmission Control) | UDP (User Datagram) | QUIC (HTTP/3) |
| :--- | :--- | :--- | :--- |
| **Connexion** | Oui (Handshake 3-Way) | Non (Sans état) | Oui (Combiné avec TLS 1.3) |
| **Garantie d'ordre** | Oui (Strict au niveau flux) | Non | Oui (Par flux indépendant) |
| **Head-of-Line Blocking** | Oui (Bloque tous les paquets) | Non | Non (Isolé par stream) |
| **Temps d'établissement** | 1 RTT (+ 1 RTT TLS) | 0 RTT | 1 RTT (ou 0-RTT en reprise) |
| **Usage Typique** | HTTP/1.1, HTTP/2, SSH, SQL | DNS, WebRTC, Gaming | HTTP/3, CDN Cloudflare, YouTube |

Maîtriser ces concepts fondamentaux permet de concevoir des architectures résilientes, de diagnostiquer les pannes réseau réelles et de configurer sereinement vos proxies et serveurs de production.
