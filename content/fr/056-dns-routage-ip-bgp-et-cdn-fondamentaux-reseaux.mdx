# DNS, Routage BGP et CDN : Les Dessous d'Internet pour Développeurs

Vous venez de lancer une migration critique de serveurs en production. Vous modifiez votre enregistrement DNS pour pointer vers la nouvelle infrastructure cloud, et immédiatement, les utilisateurs crient au scandale : 

La moitié d'entre eux atterrit sur le nouveau cluster, l'autre moitié sur l'ancien serveur en cours de démantèlement, et votre chef d'équipe vous répète le vieux poncif : *« C'est normal, la propagation DNS prend entre 24 et 48 heures. »*

En réalité, la prétendue « lenteur de propagation DNS » n'est presque jamais une fatalité : c'est le résultat d'une mauvaise compréhension du **TTL**, des caches récursifs et de la topologie réseau d'Internet.

Pour concevoir des architectures résilientes, configurer des VPC Cloud sans collision d'adresses et exploiter pleinement les CDN, voici ce que tout développeur doit maîtriser sur le **DNS, le routage BGP et l'Edge Computing**.

## 1. L'Arbre Généalogique de la Résolution DNS

Le DNS n'est pas un serveur centralisé magique. C'est une gigantesque **base de données arborescente et hiérarchique distribuée** à l'échelle planétaire.

```txt
                       [ . (Serveurs Racine / Root) ]
                                      │
            ┌─────────────────────────┴─────────────────────────┐
      [ .com TLD ]                                        [ .fr TLD ]
            │                                                   │
   [ mondomaine.com ]                                     [ societe.fr ]
 (Serveur Autoritaire)                                 (Serveur Autoritaire)
```

### Le Voyage d'une Requête de Résolution :
1. **Cache Local :** Le navigateur regarde son propre cache mémoire, puis interroge le résolveur de l'OS (`/etc/hosts`, `systemd-resolved`).
2. **Résolveur Récursif (ISP / DNS Public) :** Si la réponse est absente, l'OS contacte le résolveur configuré (votre box opérateur, `1.1.1.1` de Cloudflare ou `8.8.8.8` de Google).
3. **Serveur Racine (`.`):** Il y a 13 groupes de serveurs racine dans le monde. Ils ne connaissent pas votre IP, mais indiquent au résolveur où trouver les serveurs du TLD correspondant (ex: `.com`).
4. **Serveur TLD (`.com`) :** Géré par des registres (comme Verisign pour `.com`), il renvoie les serveurs de noms faisant autorité (**Authoritative Nameservers**, ex: `ns1.cloudflare.com`).
5. **Serveur Autoritaire :** Il détient le fichier de zone officiel de votre domaine et renvoie l'adresse IP finale (`A` ou `AAAA`).

## 2. Les Enregistrements DNS Indispensables

Chaque développeur manipule régulièrement ces types d'enregistrements :

| Type | Rôle | Exemple de Valeur |
| :--- | :--- | :--- |
| **A** | Associe un nom d'hôte à une adresse IPv4 | `api.mondomaine.com -> 198.51.100.42` |
| **AAAA** | Associe un nom d'hôte à une adresse IPv6 | `api.mondomaine.com -> 2001:db8::1` |
| **CNAME** | Alias pointant vers un autre nom d'hôte | `www -> mondomaine.com` |
| **ALIAS / ANAME** | Pseudo-CNAME aplati à la racine (`apex / @`) | Permet de pointer `@` vers un DNS tiers |
| **TXT** | Stocke des métadonnées texte arbitraires | Validation de domaine, SPF (`v=spf1 ...`), DKIM |
| **MX** | Serveurs de messagerie électronique prioritaires | `10 mail.mondomaine.com` |

> [!WARNING]
> La spécification DNS (RFC 1034) **interdit formellement** de placer un enregistrement `CNAME` à la racine d'un domaine (`@` ou `mondomaine.com`), car un CNAME ne peut cohabiter avec aucun autre enregistrement (comme `MX` ou `NS`). C'est pourquoi les hébergeurs modernes proposent l'« aplatissement CNAME » (*CNAME Flattening*) ou enregistrement `ALIAS`.

## 3. Démystifier le TTL : Pourquoi la "Propagation" N'Existe Pas

Le **TTL (Time-To-Live)** indique le nombre de secondes pendant lesquelles les résolveurs récursifs et navigateurs ont le droit de conserver la réponse en cache avant de réinterroger votre serveur autoritaire.

- Si votre TTL est de `86400` (24 heures) et que vous changez votre IP, les clients continueront d'interroger l'ancienne machine pendant 24 heures.
- **La bonne pratique de migration :** 72 heures *avant* une bascule de serveur, abaissez votre TTL à `60` ou `300` secondes. Le jour J, la bascule prendra moins d'une minute sur l'ensemble du globe. Une fois la migration validée, remontez le TTL à `3600` pour soulager vos serveurs DNS.

## 4. Adressage IP et Notation CIDR pour Développeurs

Lorsque vous configurez un réseau privé virtuel (AWS VPC, réseau Docker ou sous-réseau Kubernetes), vous croisez obligatoirement la notation **CIDR (Classless Inter-Domain Routing)**.

Le préfixe (ex: `/24`) indique le nombre de bits fixés pour le réseau sur les 32 bits d'une adresse IPv4 :

```txt
192.168.1.0 / 24  ──> 24 bits de réseau fixes | 8 bits réservés aux machines hôtes
                      2^(32 - 24) = 2^8 = 256 adresses IP (dont 251 ou 254 utilisables)
```

### Les 3 Plages Privées Indispensables (RFC 1918) :
Ces adresses ne sont **jamais routées sur l'Internet public**. Elles sont réservées aux réseaux internes d'entreprises et au Cloud :
- `10.0.0.0/8` : De `10.0.0.0` à `10.255.255.255` (16,7 millions d'IP — idéal pour les gros VPC cloud).
- `172.16.0.0/12` : De `172.16.0.0` à `172.31.255.255` (1 million d'IP — utilisé par défaut par Docker).
- `192.168.0.0/16` : De `192.168.0.0` à `192.168.255.255` (65 536 IP — réseau local box domestique).

## 5. Routage BGP et Anycast : Comment Fonctionne l'Échelle Mondiale

Comment Cloudflare ou Google peuvent-ils proposer une seule adresse IP publique (`1.1.1.1` ou `8.8.8.8`) accessible avec moins de 10 ms de latence à Paris, Tokyo et New York simultanément ?

La réponse réside dans le protocole **BGP (Border Gateway Protocol)** et le routage **Anycast**.

```txt
                  [ Client à Paris ]                 [ Client à Tokyo ]
                           │                                  │
                           ▼                                  ▼
               [ PoP Cloudflare Paris ]            [ PoP Cloudflare Tokyo ]
                     (IP: 1.1.1.1)                       (IP: 1.1.1.1)
```

- En mode **Unicast traditionnel**, une adresse IP correspond à une seule machine physique dans un seul datacenter.
- En mode **Anycast**, des centaines de routeurs à travers le globe diffusent la même adresse IP via BGP à leurs opérateurs voisins. Les paquets du client sont automatiquement acheminés vers le datacenter le plus proche selon les règles de routage des fournisseurs d'accès.

## 6. L'Architecture Interne d'un CDN (Content Delivery Network)

Un CDN ne se contente pas de stocker des images JPEG. C'est un reverse proxy distribué programmable.

```txt
Client Web ──> [ Edge PoP CDN ] ──(Cache MISS)──> [ Serveur Origin ]
                     │ (Cache HIT)
                     ▼
             Réponse en 15 ms
```

### Mécanismes clés de Caching HTTP :
1. **`Cache-Control: public, max-age=31536000, immutable` :** Pour les assets versionnés par hash (`app-a8f3d1.js`). Le CDN et le navigateur ne réinterrogeront jamais l'origine.
2. **`stale-while-revalidate` :** Permet au CDN de servir immédiatement une version en cache même si elle est expirée, tout en déclenchant un rafraîchissement asynchrone en arrière-plan vers l'origine.
3. **Invalidation par Tags (`Cache-Tags / Surrogate-Keys`) :** Permet d'invalider instantanément des milliers de pages associées à un produit spécifique dès qu'un admin met à jour son prix dans le backoffice.

## 7. Résolution DNS Programmatique avec Cache Local en Node.js

Par défaut, la fonction `dns.lookup()` de Node.js utilise l'appel système bloquant `getaddrinfo(3)`, ce qui peut saturer le pool de threads `libuv` lors de milliers d'appels HTTP sortants.

Voici comment implémenter un résolveur DNS asynchrone ultra-performant en TypeScript :

```typescript
import * as dns from 'node:dns/promises';

interface CachedRecord {
  readonly ip: string;
  readonly expiresAt: number;
}

export class HighThroughputDnsResolver {
  private readonly cache = new Map<string, CachedRecord>();
  private readonly defaultTtlMs = 60_000;

  public async resolveHost(hostname: string): Promise<string> {
    const now = Date.now();
    const existing = this.cache.get(hostname);

    if (existing && existing.expiresAt > now) {
      return existing.ip;
    }

    // Utilisation de resolve4() pour interroger le réseau sans bloquer le threadpool libuv
    try {
      const addresses = await dns.resolve4(hostname);
      const selectedIp = addresses[0] ?? '127.0.0.1';

      this.cache.set(hostname, {
        ip: selectedIp,
        expiresAt: now + this.defaultTtlMs,
      });

      return selectedIp;
    } catch {
      // Fallback sur valeur expirée en cas de panne réseau transitoire
      if (existing) {
        return existing.ip;
      }
      throw new Error(`DNS resolution failed for host: ${hostname}`);
    }
  }
}
```

Maîtriser le DNS, le routage IP et la mécanique des CDN permet d'éviter les pannes silencieuses lors des déploiements et de concevoir des plateformes web véritablement résilientes à l'échelle internationale.
