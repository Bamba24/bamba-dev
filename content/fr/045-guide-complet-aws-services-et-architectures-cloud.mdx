# Guide Complet AWS : Services Essentiels et Architecture

« *Nous avons laissé notre cluster de bases de données et nos instances de calcul ouverts sur Internet avec l'utilisateur root sans MFA.* »

Ce témoignage glaçant est le scénario catastrophe classique qui mène à des factures de plusieurs dizaines de milliers de dollars générées par des mineurs de cryptomonnaies ou au piratage intégral des données clients.

Avec plus de 200 services managés, **Amazon Web Services (AWS)** est le leader incontesté de l'infrastructure cloud mondiale. Mais cette puissance s'accompagne d'une complexité redoutable. Naviguer dans le catalogue AWS sans carte d'ingénierie conduit inévitablement au gaspillage financier et aux failles de sécurité.

Dans ce guide technique de référence, nous allons disséquer les services essentiels d'AWS (IAM, VPC, EC2, S3, RDS, Lambda) et concevoir ensemble une **architecture de production hautement disponible à 3 tiers**, sécurisée et conforme aux meilleures pratiques du *Well-Architected Framework*.

## 1. L'Infrastructure Globale d'AWS

L'infrastructure physique d'AWS repose sur trois niveaux géographiques interconnectés par un réseau privé fibré ultra-rapide :

1. **Régions (Regions)** : Zones géographiques distinctes dans le monde (ex: `eu-west-3` à Paris, `us-east-1` en Virginie). Chaque région est totalement isolée des autres pour garantir la souveraineté des données.
2. **Zones de Disponibilité (Availability Zones - AZ)** : Chaque région contient au minimum 3 datacenters distincts, séparés physiquement par plusieurs dizaines de kilomètres pour résister aux incendies ou inondations, mais reliés par de la fibre à très faible latence (moins de 2 ms).
3. **Points de Présence (Edge Locations)** : Des centaines de points de terminaison répartis dans les grandes métropoles mondiales pour mettre en cache le contenu statique via le CDN **Amazon CloudFront**.

## 2. Sécurité Fondamentale : AWS IAM (Identity and Access Management)

La sécurité sur AWS repose sur une règle d'or : **le principe de moindre privilège**.

```txt
┌────────────────────────────────────────────────────────────────────────┐
│                        HIÉRARCHIE DE SÉCURITÉ IAM                      │
├────────────────────────────────────────────────────────────────────────┤
│ COMPTE ROOT (Verrouillé avec MFA physique, JAMAIS utilisé au quotidien)│
│       │                                                                │
│       ├──► IAM Users (Identités humaines pour les ingénieurs)          │
│       ├──► IAM Groups (Regroupement : Developers, Admins, SecOps)      │
│       └──► IAM Roles (Identités assumées par les machines ou services) │
│                 │                                                      │
│                 ▼                                                      │
│           IAM Policies (Contrats JSON définissant Allow / Deny)        │
└────────────────────────────────────────────────────────────────────────┘
```

### Règles d'Or IAM
- **Verrouiller le compte Root** : Activer immédiatement l'authentification multi-facteurs (MFA) et ranger la clé dans un coffre-fort.
- **Privilégier les IAM Roles** : N'injectez jamais de clés d'accès permanentes (`AWS_ACCESS_KEY_ID`) dans vos serveurs ou conteneurs. Attachez un **IAM Role** à votre instance EC2 : AWS gère et renouvelle automatiquement des jetons éphémères sécurisés.
- **Politiques déclaratives au format JSON** : Définissez explicitement les actions et les ressources cibles :

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3InvoiceRead",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::bambadev-invoices-bucket",
        "arn:aws:s3:::bambadev-invoices-bucket/*"
      ]
    }
  ]
}
```

## 3. Réseau Étanche : Amazon VPC (Virtual Private Cloud)

Le **VPC** est votre centre de données privé virtuel et hermétique au sein d'AWS.

- **Subnets Publics** : Connectés à l'extérieur via une **Internet Gateway (IGW)**. Ils hébergent les répartiteurs de charge (*Application Load Balancers*).
- **Subnets Privés** : Sans adresse IP publique. Les serveurs d'application y résident. Pour accéder à Internet (télécharger des mises à jour système), ils transitent par une **NAT Gateway** située dans le sous-réseau public.
- **Security Groups vs Network ACLs** :
  - *Security Group (Stateful)* : Pare-feu virtuel attaché directement à une instance réseau (ex: autoriser le port 443 en entrée autorise automatiquement la réponse en sortie).
  - *Network ACL (Stateless)* : Pare-feu au niveau du sous-réseau, analysant chaque paquet indépendamment à l'entrée et à la sortie.

## 4. Les Piliers du Calcul (Compute) et du Stockage (Storage)

### 4.1 Compute : Du Serveur Dédié au Serverless
- **Amazon EC2 (Elastic Compute Cloud)** : Serveurs virtuels redimensionnables à la demande. Combinés aux *Auto Scaling Groups*, ils ajustent automatiquement leur nombre selon l'affluence des utilisateurs.
- **AWS Lambda (Serverless)** : Exécution de code à la demande sans aucun serveur à administrer. Vous êtes facturé uniquement aux 100 millisecondes d'exécution réelle. Idéal pour les API événementielles et les traitements d'images en arrière-plan.
- **Amazon ECS / EKS** : Hébergement de conteneurs Docker managés, avec l'option **AWS Fargate** pour éliminer la maintenance des machines sous-jacentes.

### 4.2 Storage : Blobs, Blocs et Fichiers
- **Amazon S3 (Simple Storage Service)** : Stockage d'objets immuable offrant une durabilité de 99.999999999% (11 9s). Idéal pour les fichiers statiques, images, sauvegardes et logs.
- **Amazon EBS (Elastic Block Store)** : Disques durs SSD virtuels à haute performance attachés directement à vos instances EC2.

### 4.3 Bases de Données : RDS et DynamoDB
- **Amazon RDS (Relational Database Service)** : Moteurs PostgreSQL, MySQL ou MariaDB managés avec bascule automatique haute disponibilité (*Multi-AZ Failover*) et sauvegardes automatisées quotidiennes.
- **Amazon DynamoDB** : Base de données NoSQL distribuée sans serveur, garantissant des temps de réponse à un chiffre en milliseconde quelle que soit l'échelle.

## 5. L'Analogie du Monde Réel : Le Château Fort Moderne

> **L'Analogie de la Banque Fortifiée :**
> - Le **VPC** est l'**enceinte fortifiée** du château avec ses douves et ses ponts-levis.
> - La **Région et les AZ** sont des **bâtiments distincts** répartis sur le domaine pour qu'un incendie dans une aile n'interrompe jamais l'activité des autres.
> - **IAM** est le **système de badges biométriques et d'habilitation de sécurité** : chaque employé n'a accès qu'à son bureau assigné.
> - Le **Public Subnet et l'ALB** sont le **hall d'accueil et les hôtesses** : ils accueillent les visiteurs publics, vérifient leur identité et les orientent.
> - Le **Private Subnet et EC2** sont les **bureaux de gestion internes** protégés des regards extérieurs.
> - **Amazon RDS et S3** sont la **chambre forte ultra-sécurisée au sous-sol**, accessible uniquement par les fondés de pouvoir internes via un sas blindé.

## ❓ FAQ Schema : Questions Fréquentes sur AWS

### Quelle est la différence entre AWS Fargate et EC2 pour faire tourner des conteneurs ?
Avec **EC2**, vous gérez vous-même les serveurs virtuels hôtes (mises à jour de sécurité de l'OS, dimensionnement de la mémoire). Avec **AWS Fargate**, l'infrastructure est entièrement abstraite : vous spécifiez uniquement la quantité de CPU et de RAM dont votre conteneur a besoin, et AWS l'exécute sans aucun serveur à configurer.

### Comment éviter les mauvaises surprises de facturation sur AWS ?
Activez immédiatement **AWS Budgets** pour recevoir des alertes par e-mail dès que vos dépenses prévisionnelles atteignent 80% de votre plafond. Mettez également en place des règles de cycle de vie sur S3 (*Lifecycle Policies*) pour archiver automatiquement les anciens fichiers vers Amazon Glacier.

### Pourquoi utiliser une NAT Gateway plutôt qu'une adresse IP publique sur mes serveurs ?
Une adresse IP publique expose directement votre serveur aux scanners de vulnérabilités et aux attaques par force brute venues d'Internet. La **NAT Gateway** permet à vos serveurs situés dans des sous-réseaux privés d'initier des connexions vers l'extérieur (ex: mises à jour de sécurité) tout en interdisant formellement à Internet d'initier une connexion entrante vers eux.
