# Practical Enterprise Git Use Cases: From Daily Emergencies to Advanced Workflows

Every developer knows the three fundamental commands: `git add`, `git commit`, and `git push`. But in fast-paced software teams, real-world development challenges are far more complex:
- *"A critical bug just landed in production while I have 12 unfinished files on my branch. What do I do?"*
- *"I made a typo in my previous commit message. How do I fix it without polluting history?"*
- *"A regression was introduced two weeks ago across 400 commits. How do I pinpoint the cause quickly?"*
- *"I accidentally deleted an unpushed local branch. Is my code lost forever?"*

This guide covers the **9 most frequent enterprise Git use cases**, providing exact commands and best practices so you never fear manipulating your Git repository.

## Use Case 1: Modify or Undo Your Last Local Commit

### Scenario
You committed your changes, but realized you forgot an environment configuration file, or left a typo in the commit message.

### Solution A: Add the forgotten file without creating a new commit
```bash
# 1. Stage the missing file
git add config/settings.json

# 2. Merge it into the previous commit without altering its message
git commit --amend --no-edit
```

### Solution B: Edit the previous commit message
```bash
git commit --amend -m "feat(auth): implement two-factor authentication flow"
```

### Solution C: Undo the commit while keeping all changes staged in your IDE
```bash
# Uncommits changes but leaves them safely staged in the index
git reset --soft HEAD~1
```

> **Golden Rule:** Only amend or reset commits that are **local and unpushed** to shared remote branches.

## Use Case 2: Safely Undo a Commit Already Deployed to Production

### Scenario
A broken commit was merged into `main` and deployed to production. You must undo the changes immediately.

### Why `git reset` is dangerous here
Running `git reset --hard` on a shared branch rewrites public Git history and breaks your team's local branches.

### The Clean Solution: `git revert`
`git revert` creates a **new inverse commit** that precisely rolls back the offending changes while preserving immutable history:

```bash
# Reverts the specified commit cleanly
git revert a1b2c3d -m "revert: temporary rollback of payment integration"

# Deploy fix immediately
git push origin main
```

## Use Case 3: Handle Sudden Emergencies Mid-Task (Advanced Git Stash)

### Scenario
You are halfway through a complex refactor with 8 uncommitted files. A critical priority requires immediate attention on `main`. You cannot commit broken code, nor can you afford to lose your progress.

### The Workflow
```bash
# 1. Save work-in-progress with an explicit label
git stash push -m "WIP: checkout flow refactoring"

# 2. Your working tree is now clean! Switch branches safely:
git checkout main
# ... fix the issue, commit, and push ...

# 3. Return to your feature branch
git checkout feature/checkout

# 4. Restore your files and pop them from the stash index
git stash pop
```

## Use Case 4: Import a Specific Fix from Another Branch (`cherry-pick`)

### Scenario
A teammate solved a critical bug on `feature/redesign`. You need that specific bugfix on your `feature/api-v2` branch right now, but you cannot merge their entire branch because it contains unfinished work.

```txt
Teammate Branch:  ---(A)---(B: Bugfix)---(C: Experimental)
                               │
                    git cherry-pick B
                               ▼
Your Branch:      ---(X)---(Y)---(B': Bugfix applied cleanly!)
```

### The Solution
```bash
# Replays the exact changes of commit B onto your current branch
git cherry-pick b4c5d6e
```

## Use Case 5: Clean Up Commit History Before a Merge Request (`rebase -i`)

### Scenario
Over 3 days of development, you created messy intermediate commits: `wip`, `typo`, `tests`, `fix again`. Submitting this history for code review is bad engineering practice.

### The Solution: Interactive Rebase
```bash
# Open interactive editor for the last 4 commits
git rebase -i HEAD~4
```

Mark trailing commits with **`squash`** (or `s`):
```txt
pick 1a2b3c4 feat(cart): add cart interface
squash 5d6e7f8 fix typo in component
squash 9a0b1c2 fix unit tests
squash 3d4e5f6 styling tweaks
```

Save and exit: Git combines all 4 commits into **a single clean, atomic commit**.

## Use Case 6: Resolve Rebase Conflicts Without Panic

### The Step-by-Step Resolution:
```bash
# 1. Inspect conflicted files
git status

# 2. Open conflicted files in your IDE and resolve markers:
#    <<<<<<< HEAD (Upstream changes)
#    =======
#    >>>>>>> your-commit (Your changes)

# 3. Stage the resolved files:
git add src/app.ts

# 4. DO NOT run "git commit"! Continue the rebase:
git rebase --continue
```

> **Escape Hatch:** If conflicts get tangled and you want to abort:
> ```bash
> git rebase --abort
> ```

## Use Case 7: Find a Regression Among 500 Commits in 9 Steps (`git bisect`)

### Scenario
The application worked properly in release `v1.2.0`. Today on `main`, a feature is broken. 500 commits were merged between then and now.

### The Solution: Binary Search with `git bisect`
Instead of testing 500 commits one by one, Git tests the exact midpoint in 9 automated steps ($2^9 = 512$):

```bash
git bisect start
git bisect bad             # Current version is broken
git bisect good v1.2.0     # Known working baseline

# Git checks out commit #250. Test your build:
# If it works:
git bisect good
# If broken:
git bisect bad

# Git narrows down the culprit:
# "a8f3b9c is the first bad commit"

git bisect reset
```

## Use Case 8: Work on Two Branches Simultaneously Without Re-cloning (`git worktree`)

### Scenario
You are running a 15-minute compilation on `feature/migration`. A teammate asks you to review a bug on `staging` right now.

Instead of stashing and running slow `npm install` re-indexing, use `git worktree`:

```bash
# Checkout the staging branch into a parallel directory
git worktree add ../hotfix-folder staging

# Open ../hotfix-folder in a new IDE window simultaneously!

# When finished:
git worktree remove ../hotfix-folder
```

## Use Case 9: Recover Accidentally Deleted Code (`git reflog`)

### Scenario
You ran a destructive `git reset --hard` or accidentally deleted a local branch. Your unpushed code seems gone.

### The Reality: Git Never Deletes History Immediately
Git keeps an internal journal of **every single `HEAD` movement**: the **Reflog**. Commits remain accessible in memory for 30 to 90 days before garbage collection runs.

```bash
# View chronological history of HEAD pointers
git reflog
```

Locate the commit right before your mistake (`HEAD@{1}`) and restore it:
```bash
git reset --hard HEAD@{1}
```
Your code is instantly recovered in your working directory.

| :--- | :--- |
| **Fix last unpushed commit** | `git commit --amend --no-edit` |
