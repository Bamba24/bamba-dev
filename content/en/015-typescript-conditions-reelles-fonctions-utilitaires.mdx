# TypeScript in the Real World: Why Your Utility Functions Crash in Production

Every developer has encountered this scenario: `tsc --noEmit` reports 0 errors, your CI pipeline turns green, and minutes after deployment, Sentry alerts start firing:

```txt
💥 Uncaught TypeError: value.toLowerCase is not a function
💥 Uncaught TypeError: Cannot read properties of undefined (reading 'replace')
```

How does statically typed code fail so spectacularly at runtime?

In this article, we examine API contract polymorphism, the dangers of blind type assertions, and how to write resilient utility functions that never crash.

---

## 1. API Polymorphism vs Compiler Assumptions

TypeScript performs static analysis at build time. In the browser, **TypeScript is stripped away**: raw JavaScript executes whatever the server returned.

```typescript
// ❌ Fragile function: assumes input always strictly conforms
export function formatBadge(role: string): string {
  return role.toUpperCase().trim();
}
```

If an API response contains `null` (user has no role yet) or a numeric enum `1`, this function will throw an unhandled exception.

### The Toxic Habit: Blind Type Assertions (`as`)

```typescript
// ❌ Dangerous: deliberately lying to the compiler
const userRole = (apiResponse.role as unknown as string).toUpperCase();
```

Using `as unknown as T` or the non-null assertion `!` disables TypeScript's safety mechanisms, turning compile-time errors into runtime production outages.

---

## 2. The Hidden Trap of `filter(Boolean)`

To strip null values from a list (`Array<User | null | undefined>`), developers often write:

```typescript
// ❌ The filter(Boolean) trap
const activeUsers = rawUsers.filter(Boolean);
```

### Why this is problematic:
1. **Incomplete Type Narrowing**: Under many TS configurations, TypeScript cannot guarantee that `null` was removed from the inferred type.
2. **Accidental Removal of Valid Falsy Values**: `Boolean()` removes number `0`, empty string `""`, and boolean `false`!

### The Solution: Explicit Type Guard

```typescript
// ✅ Bulletproof predictive type guard
const cleanUsers = rawUsers.filter(
  (user): user is NonNullable<typeof user> => user != null
);
```

Using `!= null` strips both `null` and `undefined` while preserving legitimate zeros and empty strings.

---

## 3. Writing Resilient Defensive Utilities

```typescript
export function safeTruncate(value: unknown, maxLength = 50): string {
  if (typeof value !== 'string') {
    return '';
  }

  const trimmed = value.trim();
  if (trimmed.length <= maxLength) {
    return trimmed;
  }

  return `${trimmed.slice(0, maxLength)}…`;
}
```

Using `value: unknown` enforces runtime validation before calling methods.

---

## Summary

1. Ban `any` and forced assertions (`as unknown as T`).
2. Replace `filter(Boolean)` with `(x): x is NonNullable<typeof x> => x != null`.
3. Centralize and reuse shared utilities in `lib/utils/` instead of duplicating variations in component files.
